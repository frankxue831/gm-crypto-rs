# v1.11 scope — RustCrypto `aead` 0.6 trait fit for SM4-GCM / SM4-CCM

**Status:** scope proposed; forks **Q11.1–Q11.10 await maintainer sign-off**
before any code lands. Recommendations below are the agent's, with alternatives
recorded so a different choice stays cheap.

**Cycle type:** publishing. Workspace `1.9.1` → **`1.11.0`**; crates.io skips
`1.10.0` (v1.10 was the non-publishing assurance cycle — the v0.14 → v0.15
precedent). Sibling pins `=1.11.0`. Publish order simd → core → c, the
maintainer's authenticated per-release call.

**Numbering note.** `Q11.x` collides with `docs/v0.11-scope.md`'s `Q11.1–Q11.11`.
That is the house style — `docs/v1.10-scope.md` reuses `Q10.x` over
`docs/v0.10-scope.md`, and v1.9 reused `Q9.x`. References are always
doc-qualified ("`docs/v1.11-scope.md` Q11.2").

---

## 1. Why now

`CLAUDE.md`'s deferred list has carried "RustCrypto `aead` trait fit
(**blocked**: aead still 0.6.0-rc.10)" since v0.11. **That block is discharged:**
`aead` **0.6.1** is stable on crates.io. Two further facts make this cycle cheap
rather than speculative:

- **The dependency line already exists in our tree.** `aead` 0.6.1 requires only
  `crypto-common ^0.2` and `inout ^0.2.2`, both of which v0.11 already pulled in
  when it moved to `digest 0.11` / `cipher 0.5`. `aead` itself is the *only* new
  crate. Its MSRV is **1.85** — exactly the workspace MSRV — and it is `no_std`.
- **`aes-gcm` 0.11.0 stable ships on `aead` 0.6**, so the trait generation we are
  fitting is the one the ecosystem actually consumes.

One asymmetry to record honestly: RustCrypto's own `ccm` crate is still at
`0.6.0-rc.3` on this line. We would ship a stable-on-`aead`-0.6 CCM trait fit
before upstream does. We borrow its **type shape** (sealed size traits) as
precedent, not its stability.

**What this cycle is not.** No new cryptography. Every trait method is a thin
wrapper over the existing, audited `mode_gcm` / `mode_ccm` bodies. Default-features
build stays byte-identical; the whole surface sits behind a new opt-in feature.

## 2. The `aead` 0.6.1 surface (pinned — verified against docs.rs 2026-08-01)

```rust
pub trait AeadCore {
    type NonceSize: ArraySize;        // hybrid-array, not bare typenum
    type TagSize:   ArraySize;
    const TAG_POSITION: TagPosition;  // { Postfix, Prefix }
}

pub trait AeadInOut: AeadCore {
    // REQUIRED — the only two methods we write:
    fn encrypt_inout_detached(&self, nonce: &Nonce<Self>, aad: &[u8],
                              buffer: InOutBuf<'_, '_, u8>) -> Result<Tag<Self>>;
    fn decrypt_inout_detached(&self, nonce: &Nonce<Self>, aad: &[u8],
                              buffer: InOutBuf<'_, '_, u8>, tag: &Tag<Self>) -> Result<()>;
    // PROVIDED: encrypt_in_place / decrypt_in_place over &mut dyn Buffer
}

#[cfg(feature = "alloc")]
impl<T: AeadInOut> Aead for T { ... }   // BLANKET
```

Load-bearing consequences:

1. **`AeadInOut` is the mandatory entry point.** Because `Aead` is
   *blanket-implemented* over it, a direct `impl Aead for Sm4Gcm` **cannot
   compile** — it would conflict. Implement `AeadInOut`; the Vec-returning
   `Aead` and the in-place methods arrive for free. Do not let a later review
   "simplify" this.
2. **`AeadInPlace` is deprecated legacy** in 0.6 — do not implement or mention it.
3. **There is no `aead::stream` module** in 0.6 (extracted to a separate crate),
   so `sm4::gcm_streaming` stays inherent-only and out of scope.
4. **`aead::Error` is an opaque unit struct.** The workspace's single-failure
   invariant crosses the trait boundary *by construction* — there is no
   "helpful" variant to accidentally add.
5. `aead::consts` re-exports the typenum `U*` constants and `aead::array` the
   `hybrid-array` types, so no direct `typenum` / `hybrid-array` dependency.

## 3. Forks for sign-off

### Q11.1 — New public types and where they live
**Recommend:** `Sm4Gcm` and `Sm4Ccm<M, N>`, each holding `key: [u8; KEY_SIZE]`,
defined in `#[cfg(feature = "aead-traits")] mod aead_impl { … }` blocks inside
`mode_gcm.rs` and `mode_ccm.rs` respectively — the exact shape of the existing
`cipher.rs::cipher_impl` / `sm3.rs::digest_impl` / `hmac.rs::digest_impl`
precedents — `pub use`d up through `sm4::`.
*Why the key and not an `Sm4Cipher`:* the free functions take `&[u8; KEY_SIZE]`,
so holding the cipher would mean either re-deriving the key or duplicating the
schedule logic. Holding key bytes keeps the wrapper provably thin (Q11.8).
**Alternative:** one new file `sm4/aead_traits.rs` for both. Cleaner single diff,
but splits the CCM sealed traits from the `VALID_TAG_LENS` / `MIN_NONCE_LEN` /
`MAX_NONCE_LEN` consts they must mirror, and breaks the trait-fit-lives-with-the-
primitive precedent.
**Note for review:** unlike `digest_impl`/`cipher_impl`, which contain impls
only, these modules introduce *public types* — the `pub use` out of a private
module is new here.

### Q11.2 — CCM parameterization
**Recommend:** `pub struct Sm4Ccm<M = U16, N = U12>` with two **sealed** public
traits — `CcmTagSize` implemented for exactly `U4, U6, U8, U10, U12, U14, U16`
(mirroring `VALID_TAG_LENS`) and `CcmNonceSize` for `U7..=U13` (mirroring
`MIN_NONCE_LEN`/`MAX_NONCE_LEN`) — plus `#[zeroize(skip)] PhantomData<(M, N)>`.
This is the `ccm` crate's shape. Validity moves to compile time; the defaults
give a bare `Sm4Ccm` canonical profile. Add `const _: () = assert!(…)`
cross-checks so the trait impls and the runtime consts cannot drift apart.
*Const-generic `usize` parameters are not viable:* `AeadCore`'s associated types
must **be** `ArraySize` types, so typenum parameters are forced.
**Alternative:** a fixed canonical `Sm4Ccm` (U16/U12 only). Simplest, but CCM's
real deployments genuinely disagree on nonce length (13 B in 802.15.4/Zigbee vs
the 12 B our module doc calls the GM-interop default), so the parameterization
has authentic demand.

### Q11.3 — GCM truncated tags and non-12-byte nonces
**Recommend: out of the trait surface.** `Sm4Gcm` fixed at `NonceSize = U12`,
`TagSize = U16`, `TAG_POSITION = Postfix` — the canonical safe profile our own
module docs steer callers toward, and what RFC 8998 / TLS use. `GcmTagLen`
truncated tags ({4,8,12,13,14,15,16}) and arbitrary-length nonces stay reachable
through the inherent `mode_gcm` functions.
**Alternative:** aes-gcm's `Sm4Gcm<NonceSize = U12, TagSize = U16>` with a sealed
`GcmTagSize`. **Decide now if ever:** retrofitting generics later — even with
defaults — reshapes the type in the api-baseline and can break turbofish
inference at call sites.

### Q11.4 — Which traits
**Recommend exactly:** `KeySizeUser` (`KeySize = U16`), `KeyInit` (default
`new_from_slice` suffices — fixed 16-byte key, unlike `HmacSm3` which overrides),
`AeadCore`, `AeadInOut` (its two required methods). Received free: `Aead`
(blanket, `alloc`) and `encrypt_in_place`/`decrypt_in_place`.
Not implemented: deprecated `AeadInPlace`; `Generate` (`rand_core`-gated, we do
not need RNG here); `dev`/blobby macros (we have our own KAT style);
`aead::stream` (does not exist in 0.6).
**Recorded honestly:** "postfix-alloc `Aead` only" is *not implementable* (§2.1).
The allocation inside the inout wrappers is the honest cost of the thin-wrapper
mandate and must be documented on the impls, not hidden.

### Q11.5 — Zeroize
**Recommend:** `#[derive(Clone, Zeroize, ZeroizeOnDrop)]` on both structs
(skipping the `PhantomData`), matching `Sm4Cipher`'s own
`#[derive(Clone, Zeroize, ZeroizeOnDrop)]`. **No `Debug` derive** over key bytes
(a manual opaque impl is acceptable, the aes-gcm shape). Additionally
`pt.zeroize()` the transient plaintext `Vec` in *both* `decrypt_inout_detached`
wrappers after copying into the out-buffer — a `Vec` drop frees but does not
scrub, and unlike the native API (which hands the `Vec` to the caller) this copy
is purely transient.
**Accepted cost, to be documented on the impls:** a per-call `Sm4Cipher::new`
key schedule, because the struct holds key bytes (Q11.1). Throughput-sensitive
callers keep the inherent API.

### Q11.6 — Feature name and wiring
**Recommend:** `aead-traits = ["sm4-aead", "dep:aead"]`, following the
`digest-traits` / `cipher-traits` naming. Dependency:
`aead = { version = "0.6.1", default-features = false, features = ["alloc"], optional = true }`.
`alloc` is **required** (both the `Aead` blanket impl and `Buffer for Vec<u8>`
are `cfg(feature = "alloc")`); default features stay **off** (default pulls
`rand_core`, surface we do not need).

### Q11.7 — Error mapping
**Recommend:** every `None` from the underlying functions → the single opaque
`Err(aead::Error)`. That covers the GCM `2^36 − 32`-byte plaintext ceiling, CCM's
length-vs-`q` gate, invalid parameters, and tag mismatch alike. The impl must
**never** distinguish them — no separate panic path, no error taxonomy in the
docs beyond "any failure". A fallible encrypt is idiomatic here (aes-gcm errors
on the same GCM bound) and costs no ergonomics, since the trait signature is
already `Result`.

### Q11.8 — Wrapper thinness (the assurance premise)
The dudect decision (Q11.9) rests on the wrappers adding no secret-dependent
work. **Pinned bodies**, to be checked verbatim at review:

- `Sm4Gcm::encrypt_inout_detached` — `mode_gcm::encrypt(&self.key, nonce, aad,
  buffer.get_in()).ok_or(Error)?`, copy ct into `buffer.get_out()`, return
  `Tag::from(tag)`. (`mode_gcm::encrypt` already returns the detached
  `(Vec<u8>, [u8; 16])` shape — no splitting needed.)
- `Sm4Gcm::decrypt_inout_detached` — `mode_gcm::decrypt(…, &tag_arr)
  .ok_or(Error)?`, copy out, `pt.zeroize()`. On failure the out-half is
  **untouched** (verify-before-decrypt means no plaintext ever materializes).
- `Sm4Ccm::encrypt_inout_detached` — `mode_ccm::encrypt(…, M::USIZE)`, split the
  returned `ct‖tag` at `pt.len()`, copy ct out, build `Tag` from the tail via
  `try_from` mapped to `Error` (**never `expect`**).
- `Sm4Ccm::decrypt_inout_detached` — join `ct‖tag` (public bytes) into a temp
  `Vec`, `mode_ccm::decrypt(…, M::USIZE)`, copy out, `pt.zeroize()`. CCM is
  decrypt-before-verify internally, but the tentative-plaintext wipe on tag
  failure already lives in `mode_ccm`; the wrapper adds nothing.

Any drift toward re-implementing mode logic in the wrapper **voids Q11.9** and
must re-open the dudect question.

### Q11.9 — Dudect: no new target (count stays 23)
**Recommend: no new dudect target.** The wrappers invoke the exact bodies that
`ct_sm4_gcm_decrypt` / `ct_sm4_ccm_decrypt` already measure — the secret-touching
code is byte-identical on the trait path. Wrapper-added work is data movement and
allocation on **public-length** data, and the only wrapper branch is on the same
success/failure bit the caller receives anyway. This is the v1.2 / v1.4 / v1.9
thin-shim rationale applied unchanged. Conditional on Q11.8 holding at review.

### Q11.10 — Test placement
**Recommend a separate `tests/rustcrypto_aead_traits.rs`** with its own
`[[test]] required-features = ["aead-traits"]`. **Do not** fold the cases into
`tests/rustcrypto_traits.rs`: that would widen its `required-features` to all
three trait features, and its existing CI leg
(`cargo test -p gmcrypto-core --features digest-traits,cipher-traits`) would then
silently stop running it — a test file that quietly stops executing is worse than
one that fails.

## 4. Assurance plan

**Fuzz — one new differential target** (`fuzz_sm4_aead_traits`, census 32 → 33).
Unlike the dudect case, the wrappers *do* contain new fallible logic worth
fuzzing: the CCM `ct‖tag` split-and-join and the generic monomorphization. One
input drives **both** the GCM trait-vs-native and `Sm4Ccm<U16,U12>`
trait-vs-native comparisons (the `fuzz_sm2_kx` multi-path pattern — no dispatch
byte), asserting byte-equality, round-trip, and agreement on failure. Key /
nonce / aad / msg carved front-consuming (pinned to `arbitrary` 1.4.2 order).
**Must ship with ≥1 committed seed** — the v1.7 lesson, where two seedless
targets ran zero inputs for 44 nights while the nightly reported `CRASH`.
`FUZZ_TARGETS` gains the name; PR #131's preflight now *enforces* that pairing.
**`fuzz/Cargo.lock` must be regenerated and committed** — it is a committed
lockfile (68 packages today, no `aead`), so enabling the feature changes it.

**KAT reuse, not new vectors.** GCM cases reuse the gmssl-derived vectors in
`tests/sm4_gcm_kat.rs`; CCM cases reuse the OpenSSL-EVP-derived vectors in
`tests/sm4_ccm_kat.rs`. The trait path must reproduce them through
`Aead::encrypt` (ct‖tag postfix concatenation). Plus: per-field tamper → `Err`;
differential vs native including empty message and empty aad;
`_inout_detached` on split buffers; the provided `encrypt_in_place` /
`decrypt_in_place` on a `Vec<u8>`; a `(M, N)` corner grid for CCM;
`Sm4Ccm<_, U13>` with a >65 535-byte plaintext → `Err`; `new_from_slice` with a
wrong-length key → `InvalidLength`. **UFCS throughout** — inherent names collide
with trait names (the standing `CLAUDE.md` gotcha).
The GCM `2^36 − 32` ceiling is untestable at integration scale (~68 GB); it stays
covered by the existing `mode_gcm` boundary unit test, with the trait mapping
doc-asserted.

**CI legs to add:** `cargo test -p gmcrypto-core --features aead-traits` (the new
`[[test]]` is required-features-gated, so a plain `cargo test --workspace` would
never run it — mirror the existing per-feature legs at `ci.yml:124-152`); a
clippy leg for the feature plus adding it to the full-matrix clippy leg; the
`cargo deny` second pass; the MSRV 1.85 all-features build list; and a wasm32
`--no-default-features --features aead-traits` leg (`aead` is `no_std`). Mirror
each into `CLAUDE.md`'s command block.

**api-baseline:** regenerating `docs/api-baseline/gmcrypto-core.txt` is expected
and **additive** — the new types and their manual trait impls appear (the
baseline already carries impl lines such as `impl digest::FixedOutput for …`).
Use the pinned `cargo-public-api 0.52.0` + `nightly-2026-05-23`, per
`api-stability.yml`. `cargo-semver-checks` (enforced ≥1.0) should pass: purely
additive.

## 5. Risks

1. **Coherence** forecloses a direct `Aead` impl (§2.1) — the single most likely
   "simplification" a reviewer or future agent would attempt. It will not compile.
2. **Upstream `ccm` is still RC** on the 0.6 line; we lead. We take its shape,
   not a stability guarantee.
3. **Alloc + per-call key schedule inside methods named "in place"** — honest-cost
   documentation is required on the impls, not silence.
4. **Transient plaintext `Vec` on the trait decrypt path** — mitigated by
   `pt.zeroize()` in both wrappers (Q11.5); a reviewer should confirm both.
5. **Baseline regeneration** must render the sealed traits and generic bounds
   cleanly under the pinned nightly. If `cargo-public-api 0.52.0` chokes, bumping
   the pin is itself a reviewed re-baseline (the `api-stability.yml` contract).
6. **MSRV 1.85 foot-guns** — no `is_multiple_of` and friends; the `cargo +1.85`
   leg gates it.

## 6. Out of scope

`aead::stream` (does not exist in 0.6 — a separate crate, and our
`gcm_streaming` decryptor is `O(message)`-memory buffered anyway, so it is not
"streaming" in that crate's sense); truncated-tag / arbitrary-nonce GCM through
the traits (Q11.3); an `aead` trait fit for SM4-XTS (XTS is not an AEAD — it is
confidentiality-only, with no tag, and must never be presented as authenticating);
any change to the inherent APIs, which stay the byte-identical source of truth.
