# v1.11.0 — ECOSYSTEM §8 Gate #1 evidence

As of the 1.11.0 candidate, `docs/ECOSYSTEM.md` §8 made the
`gmcrypto-envelope-lite` **0.1.0 RC suite** a gate on **every** `gmcrypto-core`
release, and required that "both phases' command output and the exact tested core
and envelope commits" be preserved as release evidence. This file is that record
for the 1.11.0 candidate, under the rule as it stood at the time.

That rule has since changed, and §5 below says how. The living obligation is now
the envelope gate suite **at current tip**, run in every feature configuration by
`ci/check-compatibility-gate.sh`, which produces the evidence table in place of
raw command output. Read the current `docs/ECOSYSTEM.md` §8 for the recipe a new
run must follow; read this file only as the record of the 1.11.0 run.

**Result: PASS** — no runtime or API incompatibility, so **no migration note is
required** before this release ships. One procedural note on the phase-2 injection
method is recorded in §4; it is a finding about the *gate recipe*, not about the
candidate.

## 3. Verdict

`gmcrypto-core` 1.11.0 is compatible with the `gmcrypto-envelope-lite` 0.1.0 RC
suite. The v1.11 surface is additive and entirely behind the opt-in `aead-traits`
feature, which the downstream does not enable (it pins `features = ["x509"]`), so
the candidate reaches the envelope as a byte-identical default build.

## 4. Procedural note — phase-2 injection must use a relative path

Not a candidate defect; a trap in executing the recipe. §8 says to inject "through
a temporary path dependency or Cargo `[patch]` override" and to "keep the
formatting and boundary commands unchanged". The obvious way to write that
override is an **absolute** path to the candidate checkout — and doing so makes
`./ci/check-open-source-boundary.sh` **fail**, because the absolute path embeds a
developer home directory into `Cargo.toml` and the boundary scanner exists
precisely to catch that class of leak into an export.

The failure mode is nasty because the scanner reports only
`error: open-source boundary violation` with no matched expression, which reads at
first glance like a candidate problem. It is not: removing the `[patch]` block
clears it while changing nothing about the candidate.

**Fix used here, and the recommended recipe for future gate runs:** export the
candidate core *beside* the envelope export and point the override at a relative
path (`../core/crates/gmcrypto-core`). Both boundary commands then pass unchanged,
as §8 requires. The v1.9.1 run used an absolute path and recorded phase 2 without
the two boundary commands; this run keeps them in, which is the stricter reading of
"keep the boundary commands unchanged".

## 5. Addendum (2026-08-03) — §3's premise has since expired

Nothing above is amended: every result recorded here stands as run, against the
commits named in "Tested commits".

But §3's *reason* for the PASS being trivially safe no longer holds. It reads:

> The v1.11 surface is additive and entirely behind the opt-in `aead-traits`
> feature, which the downstream does not enable (it pins `features = ["x509"]`),
> so the candidate reaches the envelope as a byte-identical default build.

On 2026-08-03 `gmcrypto-envelope-lite` 0.2.0 added an opt-in `aead` feature
defined as `["gmcrypto-core/sm4-aead"]`. The downstream now *does* enable that
core surface, and enabling it pulls `gmcrypto-simd` and `cpufeatures` into the
compiled graph. A future gate run cannot reuse this reasoning, and a
default-features-only run would no longer cover what the crate ships.

§8 was updated accordingly: the gate is no longer pinned to the downstream 0.1.0
suite, it runs every feature configuration in both phases, and it is executed by
`ci/check-compatibility-gate.sh` rather than by hand — which also encodes the
relative-path recipe from §4 above so that trap cannot recur.

## 6. Addendum (2026-08-03) — the scripted gate has now been run for real

§8 makes `ci/check-compatibility-gate.sh` the canonical recipe, but until now the
script had only ever passed its own self-test, which drives it with a fake cargo.
Its first execution against real cargo and a real core checkout would otherwise
have happened during a core release — the worst moment to discover a defect in the
thing that gates the release. It has now been run:

| Side | Commit | Notes |
|---|---|---|
| `gmcrypto-core` | `33059c4` | `main`; `crates/` and `Cargo.lock` byte-identical to release commit `613f619`, the workspace `Cargo.toml` differing only in a comment |
| `gmcrypto-envelope-lite` | `cf63612` | current tip, version 0.2.0 |

**Result: PASS**, exit 0, evidence table written. No script defect surfaced.

The comparison basis is `613f619` (the squash-merge that released 1.11.0) rather
than `6e89e722`, the commit named in "Tested commits" above: that commit no longer
exists in this repository. `release/v1.11.0` was squash-merged and deleted, and no
`v1.11.0` tag was created — the newest tag is `v1.9.0` — so the exact tested tree
is unrecoverable. §8 requires preserving "the exact tested core and envelope
commits as release evidence"; a commit reachable from no ref does not satisfy
that. Tagging each released version would.

**It reproduces this file's numbers.** Every behavioral target that existed at the
time returns an identical count — `auth_and_config` 10, `client_convenience` 15,
`key_roles` 15, `protocol_adapter` 17, `public_api` 1, `redacted_debug` 6,
`secure_client` 11, `standard_vectors` 3, `transport_types` 12 — as does
`cargo test --all-targets` at 126. The deltas that do exist are accounted for by
downstream 0.2.0 additions: one more `--lib` test, one more doc test, and a new
`aead_envelope` target that compiles to zero tests under default features because
it is `#![cfg(feature = "aead")]`.

**What this does and does not establish.** Nothing above §5 is amended; the 1.11.0
release evidence stands as run. What is new is that the released 1.11.0 core now
has a gate result against the *AEAD-enabled* downstream — `--features aead`, which
compiles `gmcrypto-core/sm4-aead` and pulls in `gmcrypto-simd`. That is the surface
§5 flagged as no longer covered, so for 1.11.0 specifically that gap is closed. It
does not close it for any future candidate; §8's pre-release run remains the only
mechanism for those.

**One downstream defect found.** The single count that moved the wrong way —
`release_documents` 13 → 12 — was not a core incompatibility but a lost regression
test in the downstream: its CRLF-normalization test was dropped when the 0.1.0
release-candidate export was imported. Recorded and repaired downstream. Worth
noting here only because it shows the evidence tables are worth diffing against
each other, not just reading once.
