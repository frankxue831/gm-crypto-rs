---

## 1. Why now

**FFI.** v0.10 cashed in the v0.9 deferral of streaming-GCM FFI with the
argument "the C ABI is permanent; the Rust streaming semantics ship first
and the ABI follows once they have settled". The v1.12 CCM pair is the same
situation one cycle later: the Rust semantics landed in 1.12.0 with the
maintainer-pinned traps closed (`q`-byte counter, `checked_add`, whole-chunk
rejection, the decryptor latch), two differential fuzz targets guard them,
and the single-shot CCM FFI (`gmcrypto_sm4_ccm_{encrypt,decrypt}`) has been
always-on since v0.23. A C caller today can stream GCM but not CCM, and the
comment block above the GCM handles in `gmcrypto-c/src/lib.rs` still says
"Streaming CCM is out of scope (CBC-MAC needs total length up-front)" — the
premise the v1.12 design overturned. This cycle projects the pair and
corrects that premise where it is written down (Q13.11).

**Zeroize.** The v1.12 review found that `Sm4CcmEncryptor`'s "wiped on
drop" posture — carried over from `Sm4Cipher` — was the *exception* in the
streaming family, not the rule. The inventory:

| Type | Key-derived or plaintext-derived state outside `Sm4Cipher` | Wipes today |
|---|---|---|
| `Sm4Cipher` | `round_keys` | **yes** (derive) |
| `Sm4CcmEncryptor` | CBC-MAC partial block (raw plaintext), running `T`, leftover keystream | **yes** (derive, v1.12) |
| `Sm4CcmDecryptor` | none — nonce, AAD, ciphertext buffer are public; `cipher` wipes itself | no derive (Q12.6: nothing to wipe) |
| `Sm4GcmEncryptor` | leftover keystream `ks`, `counter`, `j0`, and `GhashAcc { h, y, block }` — `H = E_K(0)` is key-derived and `y` is `H`-derived; `block` holds public bytes | **no** |
| `Sm4GcmDecryptor` | `j0`, `GhashAcc` (same `H`, `y`); `ct_buf` is public | **no** |
| `Sm4CtrCipher` | `leftover` keystream | **no** |
| `Sm4CbcEncryptor` | `buffer` (partial plaintext block); `output` is ciphertext | **no** |
| `Sm4CbcDecryptor` | `output` (plaintext), `held_back` (decrypted final block), `buffer` (partial ciphertext, public) | **no** |

`SECURITY.md` "Zeroization" is careful to claim only what exists, so nothing
is over-claimed today; but the natural reading of the `Sm4Cipher` doc
("zeroizes its round-key buffer on drop") by a caller who then holds a
`Sm4GcmEncryptor` is
that the *stream* is wiped too, and it is not. Closing the family in one
cycle gives the crate one sentence to say instead of a per-type table.

**Why the two ride together.** The FFI handles wrap the Rust types by value
(`Box<gmcrypto_sm4_ccm_encryptor_t { inner }>`), so `_free` and every
consuming `_finalize*` drop the Rust value; whatever the Rust type wipes,
the C caller gets for free. Landing the zeroize item first (§7) lets the
handle docs say "wiped on free" for both handles and be true at merge time.

## 2. The structural facts the design rests on

**F1 — `ZeroizeOnDrop` forbids moving fields out of `self`.** The derive
generates `impl Drop`, and Rust rejects a partial move out of a type that
implements `Drop` (E0509). Four consuming methods in the family move a field
today: `Sm4GcmEncryptor::finalize(self)` and
`Sm4GcmDecryptor::finalize_verify(self, ..)` both move `self.ghash` into
`GhashAcc::finish_with_lengths(mut self, ..)`; `Sm4CbcEncryptor::finalize(mut
self)` returns `self.output`; `Sm4CbcDecryptor::finalize(mut self)` returns
`Some(self.output)`. The precedent is `Sm4CcmEncryptor::finalize(mut self)`
(v1.12): read fields by reference, wipe temporaries, return a fresh value. Q13.14 pins the four refactors.

**F2 — `zeroize` is declared without `alloc`.** The workspace dep is
`zeroize = { version = "1.8.2", default-features = false, features =
["derive"] }`. `impl Zeroize for Vec<Z>` is behind zeroize's `alloc`
feature, so a derive on a struct with a `Vec<u8>` field does not compile
today — which is why `ccm_streaming.rs` wipes a `Vec<[u8; 16]>` with
`.iter_mut().zeroize()` and the `sm4` rule file records the workaround.
Three family types carry a `Vec<u8>` (`Sm4GcmDecryptor::ct_buf`,
`Sm4CbcEncryptor::output`, `Sm4CbcDecryptor::output`; `Sm4CcmDecryptor`
carries two). Q13.13 decides how.

**F3 — the v0.10 handle lifecycle is the only C-ABI shape in this crate.**
`_new` → `Box::into_raw` (NULL on invalid input, inside `catch_unwind`);
`_update` → `&mut *handle`; `_finalize*` → `Box::from_raw` (consume + free,
**even on error**); `_free` → abort path, NULL is a no-op; variable-length output through
the `(out, out_capacity, out_actual_len)` triple via `write_output`, which
writes the required length and returns `GMCRYPTO_ERR` when the buffer is
short. The CBC (v0.5) and GCM (v0.10) families share the lifecycle; the
CCM family gets it too. **But not every GCM symbol is the template.** GCM's
bare `_finalize` writes a fixed 16-byte `tag_out` with no triple (Q10.3),
and GCM `_update` on its `None` arm returns `GMCRYPTO_ERR` without touching
`*out_actual_len`. Only `gmcrypto_sm4_gcm_decryptor_finalize_verify`
pre-writes `0` to `*out_actual_len` so every failure arm reports zero
bytes. The templates for CCM are therefore
`gmcrypto_sm4_gcm_encryptor_finalize_with_tag_len` (triple) plus that
decryptor pre-write — Q13.3 and Q13.5 say where each applies.

**F4 — CCM's parameters are fixed at construction, GCM's tag length is
not.** `Sm4CcmEncryptor::new(key, nonce, aad, plaintext_len, tag_len)`
commits both the length and the tag length up-front (`B0` encodes both);
`Sm4GcmEncryptor` chooses the tag length at `finalize`. That is why the GCM
encryptor has two finalize symbols and the CCM encryptor needs one (Q13.5).

**F5 — what the assurance instruments cover.** `cargo-semver-checks` and
the `api-baseline` drift check cover `gmcrypto-core` and `gmcrypto-simd`
only; the C ABI's gate is the committed `include/gmcrypto.h` (regen must
not drift) plus `c_smoke`. There are no FFI fuzz targets (the fuzz
workspace depends on core only) and no FFI dudect targets — the v1.9 TLCP
FFI paragraph in `SECURITY.md` is the standing rationale for a thin shim.

## 3. Forks for sign-off

### Item A — streaming-CCM C ABI (`gmcrypto-c`)

### Q13.1 — Scope: both handles, two independent opaque types

**Recommend:** project the pair, as two independent opaque types
`gmcrypto_sm4_ccm_encryptor_t` and `gmcrypto_sm4_ccm_decryptor_t`, each
wrapping the Rust type by value (`inner: Sm4CcmEncryptor` /
`Sm4CcmDecryptor`). The v0.5 Q5.2 / v0.10 Q10.2 pin — independent types
because the two contracts differ (encrypt emits as it goes; decrypt
withholds) — applies with more force here: the CCM encryptor additionally
commits to a length. A unified `_ccm_ctx_t` with a direction enum is
rejected on the same precedent. Always-on in the C ABI (no feature; the
v0.23 posture), because `gmcrypto-c` already builds core with `sm4-aead`.

### Q13.2 — Encryptor `_new`: every CCM parameter up-front

```c
gmcrypto_sm4_ccm_encryptor_t *gmcrypto_sm4_ccm_encryptor_new(
    const uint8_t *key,            /* exactly 16 bytes */
    const uint8_t *nonce, size_t nonce_len,   /* 7..=13 */
    const uint8_t *aad,   size_t aad_len,     /* whole AAD, supplied once */
    size_t plaintext_len,          /* the length commitment (B0)       */
    size_t tag_len);               /* one of {4, 6, 8, 10, 12, 14, 16} */
```

**Recommend:** mirror `Sm4CcmEncryptor::new` one-to-one. Returns NULL on
any invalid pointer or parameter — nonce length outside `[7, 13]`,
`tag_len` outside the CCM set, `plaintext_len` that does not fit the
nonce's `q = 15 − nonce_len`-byte length field (a 13-byte nonce caps at
65 535 bytes), `aad` NULL with `aad_len > 0` — with **no distinction**
(Q13.8). The Rust `new` already gates all four; the shim adds only the
pointer checks. No incremental-AAD symbol (the Q10.6 pin; AAD is the
message header, known up-front, and the Rust API has no such path).

### Q13.3 — Encryptor `_update`: the GCM shape, plus the over-feed arm

```c
int gmcrypto_sm4_ccm_encryptor_update(
    gmcrypto_sm4_ccm_encryptor_t *enc,
    const uint8_t *pt, size_t pt_len,
    uint8_t *out, size_t out_capacity, size_t *out_actual_len);
```

**Recommend:** identical to `gmcrypto_sm4_gcm_encryptor_update` in
signature and buffer convention: the chunk's ciphertext is exactly
`pt_len` bytes; a short `out` returns `GMCRYPTO_ERR` with the required
length in `*out_actual_len` and the chunk is lost (the GCM caveat, restated
in the doc comment — size the buffer to the chunk). The CCM-specific arm:
an `update` whose cumulative length would exceed the committed
`plaintext_len` emits **nothing**, returns `GMCRYPTO_ERR`, and poisons the
handle; every later `_update` and the `_finalize` also return
`GMCRYPTO_ERR`. **On that `None` arm the shim writes `0` to
`*out_actual_len` (when non-NULL) before returning `GMCRYPTO_ERR`** — the
GCM `_update` does not, and copying it fails Q13.10 test 5; and it must not
route through `write_output(&[])`, whose empty-input path returns
`GMCRYPTO_OK`. Otherwise this is the Rust `Option::None` translated, no
more. `pt_len == 0` is a no-op returning `GMCRYPTO_OK` with
`*out_actual_len = 0`.

### Q13.4 — Decryptor `_new` / `_update`: length-free, emits nothing

```c
gmcrypto_sm4_ccm_decryptor_t *gmcrypto_sm4_ccm_decryptor_new(
    const uint8_t *key,
    const uint8_t *nonce, size_t nonce_len,
    const uint8_t *aad,   size_t aad_len);
int gmcrypto_sm4_ccm_decryptor_update(
    gmcrypto_sm4_ccm_decryptor_t *dec, const uint8_t *ct, size_t ct_len);
```

**Recommend:** the Q10.4 shape — `_update` has **no output parameters**;
plaintext appears only at `_finalize_verify`. `_new` returns NULL for a
nonce length outside `[7, 13]` (the only parameter the Rust `new` gates;
there is no tag length or plaintext length to commit — the decryptor is
length-free by the v1.12 Q12.4 design). `_update` returns `GMCRYPTO_ERR`
only on a NULL handle or an invalid input pointer; the v1.12 payload-ceiling
**latch** (buffered ciphertext past `2^(8q) − 1`) is not an `_update` error
— it is latched inside the Rust type and surfaces as `GMCRYPTO_ERR` at
`_finalize_verify`, exactly as the GCM decryptor's overflow does. The doc
comment names the 13-byte-nonce case (65 535 bytes) because it is the one
a caller can hit by accident.

### Q13.5 — Finalize: one encryptor symbol, one decryptor symbol

```c
int gmcrypto_sm4_ccm_encryptor_finalize(
    gmcrypto_sm4_ccm_encryptor_t *enc,
    uint8_t *out, size_t out_capacity, size_t *out_actual_len);
int gmcrypto_sm4_ccm_decryptor_finalize_verify(
    gmcrypto_sm4_ccm_decryptor_t *dec,
    const uint8_t *tag, size_t tag_len,
    uint8_t *out, size_t out_capacity, size_t *out_actual_len);
```

**Recommend:** the encryptor gets **one** finalize, through the output
triple, and **no** `_finalize_with_tag_len`: the tag length was committed
at `_new` (F4), so a second symbol would either repeat the argument or
contradict it. It writes the `tag_len`-byte tag; `*out_actual_len` is
pre-written to `0` (when non-NULL) so the two Rust `None` arms — poisoned,
or **under-fed** (`fed != plaintext_len`) — report zero bytes and
`GMCRYPTO_ERR`. Under-feed is the arm GCM does not have and the one the doc
comment leads with: a partial stream is never tag-authenticated, and the
handle is consumed either way. The decryptor gets the GCM
`_finalize_verify` verbatim: `tag_len` is validated against the **CCM** set
`{4, 6, 8, 10, 12, 14, 16}` (by the Rust `finalize_verify`, not by the
shim), plaintext length equals the total ciphertext fed, and the two
`GMCRYPTO_ERR` cases keep their GCM semantics — verification failure
(mismatch, bad `tag_len`, latch) writes `0`; verified-but-short-`out`
writes the required length and no plaintext, and the handle is gone, so the
caller sizes `out` to the ciphertext total up-front. Both consume + free
**on every path**, including a bad `out` pointer (the v0.5 "handle is
spent" rule).

### Q13.6 — `_free`: the abort path, NULL is a no-op

```c
void gmcrypto_sm4_ccm_encryptor_free(gmcrypto_sm4_ccm_encryptor_t *enc);
void gmcrypto_sm4_ccm_decryptor_free(gmcrypto_sm4_ccm_decryptor_t *dec);
```

**Recommend:** `Box::from_raw` + drop; NULL no-op; never after a
`_finalize*` (use-after-free, documented). Because the Rust types wipe on
drop (item B; `Sm4CcmEncryptor` already does), the doc comment may say
"the handle's key schedule and stream state are wiped on free" — with the
same best-effort caveat the Rust docs carry.

### Q13.7 — Symbol count and header

Eight symbols: `_encryptor_{new,update,finalize,free}`,
`_decryptor_{new,update,finalize_verify,free}`; two `typedef struct`
opaque types. `include/gmcrypto.h` is regenerated with
`cargo build -p gmcrypto-c --features regen-header` and committed; CI's
`git diff --exit-code` on the header is the drift gate. cbindgen emits the
doc comments, so the comments above are the C documentation — write them
for a C reader (no intra-doc links to Rust items).

### Q13.8 — Failure-mode invariant across the ABI

NULL from `_new`, `GMCRYPTO_ERR` from everything else, **no distinction**
between invalid nonce / tag length / length-field overflow / over-feed /
under-feed / poison / latch / tag mismatch / short buffer beyond what the
`*out_actual_len` convention already conveys (required length vs `0`).
This is the workspace invariant (`SECURITY.md`; `CLAUDE.md` hard
constraints); a PR that adds a code or an `errno`-style query is rejected on
that basis.

### Q13.9 — No dudect target, no fuzz target (FFI)

**Recommend: none of either.** The shim is the v1.9 / v1.11 / v1.12
thin-wrapper shape one layer out: pointer validation, `Box` lifecycle, and
a copy-out sized by public lengths, over Rust types whose own coverage
argument is in `SECURITY.md` (v1.12 paragraph: the encryptor's
secret-dependent work is the single-shot's `encrypt_block` chain; the
decryptor is a pure delegator measured by `ct_sm4_ccm_decrypt` and guarded
by `fuzz_sm4_ccm_streaming_decrypt`). The GCM streaming FFI (v0.10 Q10.8)
has neither, on the same argument. `SECURITY.md` gets one sentence appended
to the v1.12 paragraph: the v1.13 C ABI over these types adds no target,
same rationale as the v1.9 FFI. `c_smoke` is the gate (Q13.10).

### Q13.11 — Stale-premise corrections (the Q12.12 pattern)

The comment block heading the GCM streaming FFI section in `lib.rs`
("Streaming CCM is out of scope (CBC-MAC needs total length up-front)")
is corrected to point at the CCM handle section, `docs/v1.12-scope.md`
(the Rust design) and this file (the projection). The crate-level doc
comment at the top of `lib.rs` already lists single-shot CCM; it gains the
two handles **named the Q12.11 way**: a *length-committed streaming*
encryptor and an *incremental-input buffered* decryptor — the decryptor is
never called "streaming", in that comment, in the eight cbindgen comments
(Q13.7), in the example, or in the README rows. No other file in
`gmcrypto-c` or the READMEs states the old premise (checked 2026-09-04).

### Item B — zeroize across the SM4 streaming family (`gmcrypto-core`)

### Q13.12 — Scope: all seven, including `Sm4CcmDecryptor`

**Recommend:** derive `Zeroize` + `ZeroizeOnDrop` on `Sm4GcmEncryptor`,
`Sm4GcmDecryptor`, `GhashAcc`, `Sm4CtrCipher`, `Sm4CbcEncryptor`,
`Sm4CbcDecryptor`, **and** `Sm4CcmDecryptor`. The first six hold
key-derived or plaintext-derived state (§1 table) and are the point of
the item. `Sm4CcmDecryptor` holds nothing secret beyond its `cipher`, and
v1.12 Q12.6 pinned "derives nothing itself" on that ground; the reason to
reverse it is **the invariant it buys**: with all seven, the `sm4` rule and
`SECURITY.md` can state "every type under `sm4::*_streaming` /
`sm4::ccm_streaming` derives both" and a reviewer checks a derive line, not
a per-type argument about which fields are public. The cost is wiping a
public ciphertext buffer at drop — `O(message)` memory writes against an
`O(message)` decrypt — and one more `mem::take` (Q13.14). If the maintainer
prefers to keep Q12.6's per-type argument, the item is six types and the
invariant sentence gains an exception; the plan carries whichever is pinned.

### Q13.13 — `Vec<u8>` fields: enable zeroize's `alloc` feature

**Recommend:** add `"alloc"` to the workspace `zeroize` features
(`default-features = false, features = ["derive", "alloc"]`). It pulls no
crate (it is `extern crate alloc` inside zeroize, `no_std`-compatible),
gives `impl Zeroize for Vec<Z>` (wipes the elements **and the spare
capacity**, then clears — the right behaviour for a plaintext buffer that
has grown), and
lets every family type be a plain derive. The alternative —
`#[zeroize(skip)]` on each `Vec` plus a hand-written `Drop` that wipes it
— cannot coexist with the `ZeroizeOnDrop` derive on the same type, so it
would mean hand-written `Drop` + a manual `ZeroizeOnDrop` marker on three
or five types: more code on the path the item exists to make uniform.
Consequences to carry: the `sm4` rule's "`zeroize` here has no `alloc`
feature" note is rewritten (the `.iter_mut().zeroize()` in
`ccm_streaming.rs` keeps working and stays); the `wasm32` no_std builds and
the MSRV 1.85 build are in the local gate for exactly this kind of feature
flip; `cargo deny` sees no new crate. `crypto-bigint`'s own `zeroize`
feature is unaffected.

### Q13.14 — The four E0509 refactors (F1), signatures unchanged

**Recommend**, pinned so the implementer does not reach for `unsafe`,
`ManuallyDrop`, or `Option`-wrapping a field:

- `GhashAcc::finish_with_lengths(&mut self, aad_len, ct_len) -> [u8; 16]`
  (and the test-only `finish_no_lengths(&mut self)`): pad, fold the length
  block, return `self.y` — it is `Copy`. The accumulator is then dropped by
  its owner and wiped.
- `Sm4GcmEncryptor::finalize(mut self)`: `let s =
  self.ghash.finish_with_lengths(self.aad_len, self.ct_len);` then the
  existing `gctr_block`. `finalize_with_tag_len(self, ..)` calls
  `self.finalize()` — a whole-value move, not a field move; unchanged.
- `Sm4GcmDecryptor::finalize_verify(mut self, tag)`: same `&mut` call; the
  plaintext is built from `&self.ct_buf` as today; the `ct_eq` gate is
  untouched. **Nothing about the constant-time compare moves.**
- `Sm4CbcEncryptor::finalize(mut self) -> Vec<u8>`: pad, `encrypt_one`,
  `core::mem::take(&mut self.output)`.
- `Sm4CbcDecryptor::finalize(mut self) -> Option<Vec<u8>>`: **the body
  stays** — the `buffer_len != 0` reject, `let last = self.held_back?`
  (a `Copy` of `Option<[u8; 16]>`, so not a move), `strip_pkcs7_block(&last)?`,
  and the `extend_from_slice` of the stripped tail onto `self.output` —
  and only the final `Some(self.output)` becomes
  `Some(core::mem::take(&mut self.output))`. Dropping the strip or the
  extend would truncate the plaintext and skip the padding check;
  `held_back` stays on `self` so the drop wipes that plaintext block.
- `Sm4CcmDecryptor::finalize_verify(self, tag)` (if Q13.12 includes it):
  already borrows every field; only `self` → `mut self` if the compiler
  asks, else untouched.
- `Sm4CtrCipher::finalize(self)`: an empty body; untouched.

`self` → `mut self` is not a public-API change (the baseline prints
`(self)` either way) and no return type changes. A `Vec` taken by
`mem::take` leaves an empty `Vec` for the drop wipe — that is the point: the
caller now owns the plaintext and is responsible for it, as with every
returned `Vec` in the crate.

### Q13.15 — What the derive adds to the public API

Two impls per **public** type (`Zeroize`, `Drop`) — the `Sm4CcmEncryptor`
lines in `docs/api-baseline/gmcrypto-core.txt` are the shape: `impl
core::ops::drop::Drop for …` / `pub fn …::drop(&mut self)` and `impl
zeroize::Zeroize for …` / `pub fn …::zeroize(&mut self)`. That is the GCM
pair, `Sm4CtrCipher`, the CBC pair, and `Sm4CcmDecryptor` if Q13.12
includes it — twelve or fourteen lines. `GhashAcc` is a private struct in
`gcm_streaming.rs` and never appears in the baseline; do not look for it
there when the drift check runs. Additive; the
baseline is regenerated with the pinned `cargo-public-api` on the pinned
nightly (the `features-and-ci` rule) or the drift check fails. No `Clone`
is added to any streaming type (none has it today; a clone of a
mid-stream AEAD state is a nonce-reuse hazard, and `Sm4Cipher`'s `Clone`
is enough for callers who need a fresh stream). The Cargo SemVer reference
does not list adding a `Drop` impl as a breaking change; the enforced
`cargo-semver-checks` job confirms it on the PR.

### Q13.16 — Dudect: no new target; two existing targets change shape

**Recommend: no new target**, with one thing said out loud.
`ct_sm4_gcm_decrypt_buffered` drives `Sm4GcmDecryptor` and
`ct_sm4_cbc_decrypt_fanout` drives `Sm4CbcDecryptor` **inside the measured
closure, construct-to-drop**; after this change each drop also wipes its
buffers. The added work is a memset over lengths that are public and fixed
per run — the same on both classes — and `Vec::zeroize` has no
data-dependent branch. So the target bodies are unchanged in the
secret-dependent sense, but their measured constant grows, and the
PR-triggered dudect smoke runs because `crates/gmcrypto-core/src/**` is in
the trigger allowlist. Read the `RUNNER-CPU:` line first if anything
reddens (the `dudect` rule); a `|tau|` movement here is a runner story
until proven otherwise, and the gate is `|tau| ≤ 0.20`, unchanged.

## 5. Risks

- **A refactor that quietly changes a tag.** The four E0509 edits touch
  `finalize` bodies of three AEAD/CBC types. Mitigation: the existing
  chunked-equals-single-shot matrices and the KATs would catch a wrong
  byte; the fuzz sweeps are differential.
- **Moving the constant-time compare.** `Sm4GcmDecryptor::finalize_verify`
  is rewritten around `&mut self.ghash` only; the `ct_eq` line and its
  `unwrap_u8() != 1` gate are not touched (Q13.14, stated in the plan as a
  diff-level check).
- **`alloc` feature flip breaking a target.** Mitigation: the `wasm32`
  and MSRV legs in the local gate; `zeroize`'s `alloc` has no platform
  dependency.
- **Dudect movement from the added drop work** (Q13.16). Mitigation: read
  the runner line; the gate is unchanged; the work is public-length memset.
- **FFI semantics drift from the Rust pair.** Each shim call is a one-line
  delegation plus the triple; `c_smoke` tests each Rust arm through the ABI
  (Q13.10 rows 5, 6, 12 are the CCM-specific arms).
- **A caller reading "wiped on free" as a guarantee.** Both handle docs
  and the Rust docs carry the best-effort caveat; `SECURITY.md` says it
  once for the crate.
- **Header doc comments with Rust intra-doc syntax** reach the C header
  verbatim via cbindgen (the GCM comments already do, with backtick links
  that mean nothing in C). Write the eight new comments for a C reader.

## 6. Out of scope

`aead::stream` (the `aead` crate has none); an incremental-AAD symbol or any
other Rust-API change to the CCM pair; a length-declared CCM decryptor (voids
the v1.12 Q12.8 argument); a `Clone` on any streaming type (Q13.15); wiping
the single-shot functions' locals beyond what `mode_ccm::decrypt` already
does; `Sm3` / `HmacSm3` (already wipe); an XTS streaming type (none
exists); the FFI diagnostic callback (parked until a consumer exists,
2026-08-31); AVX-512 `sbox_x64` and F21 (deferred list, unchanged).
