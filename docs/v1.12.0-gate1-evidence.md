# v1.12.0 — ECOSYSTEM §8 Gate #1 evidence

`docs/ECOSYSTEM.md` §8 requires the `gmcrypto-envelope-lite` gate suite — at
current tip, in every feature configuration the crate ships, executed by its
scripted gate — to pass against every `gmcrypto-core` release candidate before
it ships. This file is that record for the **1.12.0** minor.

**Candidate of record: `9ccb262`** (squash of #187, the release-prep PR;
`main` after #185 spec, #186 implementation, #187 prep).
**Result: PASS**, both phases, both feature configurations (`default` and
`--features aead`), 0 failures. No runtime or API incompatibility, so **no
migration note is required** before this release ships.

The gate ran **once**, on 2026-09-02, against `9ccb262`.

**`RELEASE_SHA` is the tip of `main` at publish, which is a later commit than
the gated SHA** — this file's own PR (#188) already made it so, and any
documentation landing after it does the same. A gated SHA behind the release
tip is allowed; what decides whether the gate still attaches is

```
git diff 9ccb262 <RELEASE_SHA> --stat -- crates/ Cargo.toml
```

which must be **empty**. It has been empty for every commit since `9ccb262`,
all of which touched only `CLAUDE.md` and `docs/`. Were it non-empty, the
gate would be re-run against the folded tree rather than assumed to still
attach (the v1.11.2 precedent, `docs/v1.11.2-gate1-evidence.md`). Run the
check against the actual tip before tagging; that is cheaper and more
trustworthy than a SHA written here, which every later docs commit
invalidates.

The run below is the gate script's own output, unedited; the script fails
closed, so a recorded run is a passing run.

## Why this run is not content-free

Unlike the 1.11.2 patch, 1.12.0 changes code. The `crates/` + `Cargo.toml`
delta from the published 1.11.2 (`0de98e2`) to the candidate is eight files,
+882 / −47:

| File | Nature of change |
|---|---|
| `Cargo.toml`, `crates/gmcrypto-core/Cargo.toml`, `crates/gmcrypto-c/Cargo.toml` | version `1.12.0`; sibling pins `=1.12.0` — one line each |
| `crates/gmcrypto-core/src/sm4/ccm_streaming.rs` | **new**, 665 lines — `Sm4CcmEncryptor` / `Sm4CcmDecryptor` + tests, behind the existing `sm4-aead` feature |
| `crates/gmcrypto-core/src/sm4/mode_ccm.rs` | refactor: helpers promoted to `pub(super)`, shared `counter_block` / `build_a0` / `payload_ceiling`, `decrypt` split into `decrypt_with_cipher`; **public API and outputs unchanged** (OpenSSL KATs pass unmodified) |
| `crates/gmcrypto-core/src/sm4/mod.rs` | module declaration + re-export |
| `crates/gmcrypto-core/src/lib.rs` | doc comments only |
| `crates/gmcrypto-core/tests/sm4_ccm_kat.rs` | two added tests |

Two of those are exactly what this gate exists to catch, and the run settles
both:

- **The `mode_ccm` refactor is on the single-shot CCM decrypt path**, which
  the envelope depends on directly: its SM4-CCM algorithm calls
  `sm4::mode_ccm::encrypt` / `decrypt`, and its `standard_vectors` target
  drives an OpenSSL 3.x SM4-CCM baseline vector through that path under the
  `aead` configuration. In phase 2 that target ran **against the candidate**
  (`cargo test --test standard_vectors --features aead`, 5 passed) — the
  independent downstream confirmation that the refactor is byte-identical on
  the path a real consumer takes, not merely on this crate's own KATs.
- **Both sibling pins moved to `=1.12.0`.** A manifest resolves fine in its
  own workspace and can still fail through a downstream `[patch]` override —
  the v1.11.0 lesson (`docs/v1.11.0-gate1-evidence.md` §4). Phase 2's
  boundary scan against the patched tree is what proves no absolute path was
  written into the export.

Every per-target count in both phases is identical to the three 1.11.2 runs
(`docs/v1.11.2-gate1-evidence.md`) — 147/13 and 189/15 in phase 1, and the
same per-target totals across phase 2. For a release that adds public API,
counts moving would have been the signal; they did not move.

The new public types are additive. `cargo-semver-checks` against the
crates.io 1.11.2 baseline is green on #187, and `docs/api-baseline/gmcrypto-core.txt`
grew by 29 additive lines with nothing removed.

## What this gate does and does not establish

It establishes that `gmcrypto-envelope-lite` 0.4.0 at its current tip builds,
lints, and passes its full suite against this candidate in both
configurations it ships (`default` and `--features aead`).

It does **not** exercise `sm4-bitsliced-simd` — no envelope configuration
enables it — and it does **not** reach `Sm4CcmEncryptor` / `Sm4CcmDecryptor`:
the envelope's tip references no `ccm_streaming` item anywhere in its
sources. This gate therefore covers the `mode_ccm` refactor
through the envelope's single-shot CCM usage, and the manifest resolution
under the `[patch]` override; the streaming types themselves rest on this
crate's own OpenSSL KATs driven at 1-byte and 7-byte chunkings, the
`fuzz_sm4_ccm_streaming_encrypt` / `fuzz_sm4_ccm_streaming_decrypt`
differential targets, and CI. That is the intended coverage split for a
release whose new surface has no downstream consumer yet — the FFI
projection and any envelope adoption are v1.13 candidates.

It says nothing about the docs.rs render or the crates.io pages, which are
observable only after publish (the §13-style post-publish checks in
`docs/v1.11.2-release-review.md` are the template).

## Declared downstream requirement

The envelope declares `gmcrypto-core = { version = "1.11", features =
["x509"] }`. A caret `1.11` requirement admits `1.12.0` as a SemVer-compatible
minor, so **no downstream bump is required** before this candidate ships. The
script's own line confirms it below: declared requirement `1.11`, candidate
version `1.12.0`. Per §8 the disposable gate copy is pinned to `=1.12.0` so
the override resolves regardless of the declared range — the real downstream
checkout is never modified.
