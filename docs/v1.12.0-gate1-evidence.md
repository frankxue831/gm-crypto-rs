## Why this run is not content-free

Unlike the 1.11.2 patch, 1.12.0 changes code. The `crates/` + `Cargo.toml`
delta from the published 1.11.2 (`0de98e2`) to the candidate is eight files,
+882 / −47:

| File | Nature of change |
|---|---|
| `Cargo.toml`, `crates/gmcrypto-core/Cargo.toml`, `crates/gmcrypto-c/Cargo.toml` | version `1.12.0`; sibling pins `=1.12.0` — one line each |
| `crates/gmcrypto-core/src/sm4/ccm_streaming.rs` | **new**, 665 lines — `Sm4CcmEncryptor` / `Sm4CcmDecryptor` + tests, behind the existing `sm4-aead` feature |
| `crates/gmcrypto-core/src/sm4/mode_ccm.rs` | refactor: helpers promoted to `pub(super)`, shared `counter_block` / `build_a0` / `payload_ceiling`, `decrypt` split into `decrypt_with_cipher`; **public API and outputs unchanged** (OpenSSL KATs pass unmodified) |
| `crates/gmcrypto-core/src/sm4/mod.rs` | module declaration + re-export |
| `crates/gmcrypto-core/src/lib.rs` | doc comments only |
| `crates/gmcrypto-core/tests/sm4_ccm_kat.rs` | two added tests |

Two of those are exactly what this gate exists to catch:

- The `mode_ccm` refactor is on the single-shot CCM decrypt path. The
  envelope's `aead` configuration compiles `gmcrypto-core/sm4-aead` and pulls
  `gmcrypto-simd` into the graph; whatever SM4-CCM the envelope's own suite
  exercises now runs through `decrypt_with_cipher`. This crate's KATs and
  fuzz sweeps say the refactor is byte-identical; the gate is the independent
  downstream confirmation.
- Both sibling pins moved to `=1.12.0`. A manifest resolves fine in its own
  workspace and can still fail through a downstream `[patch]` override — the
  v1.11.0 lesson (`docs/v1.11.0-gate1-evidence.md` §4). Phase 2's boundary
  scan against the patched tree is what proves no absolute path was written
  into the export.

The new public types are additive. `cargo-semver-checks` against the
crates.io 1.11.2 baseline is green on #187, and `docs/api-baseline/gmcrypto-core.txt`
grew by 29 additive lines with nothing removed.

## What this gate does and does not establish

It establishes that `gmcrypto-envelope-lite` at its current tip builds,
lints, and passes its full suite against this candidate in both
configurations it ships (`default` and `--features aead`).

It does **not** exercise `sm4-bitsliced-simd` — no envelope configuration
enables it — and it exercises `Sm4CcmEncryptor` / `Sm4CcmDecryptor` only if
the envelope's suite calls them. `[maintainer: state whether the envelope
reaches the streaming types at its current tip; if it does not, this gate
covers the `mode_ccm` refactor path through the envelope's single-shot CCM
usage and the manifest resolution, and the streaming types rest on this
crate's own KATs, differential fuzz targets, and CI.]`

It says nothing about the docs.rs render or the crates.io pages, which are
observable only after publish (the §13-style post-publish checks in
`docs/v1.11.2-release-review.md` are the template).
