# v1.11.2 release review checklist (three-crate workspace)

The reviewer runbook for the **1.11.2** publish. Deliberately short. Its
predecessors each had a substantive headline question — 1.9.1's was "is the
licence text actually in the archive?", 1.11.0's "is it genuinely additive?",
1.11.1's "is the default build genuinely wire-identical while both opt-in
paths are genuinely fixed?". **1.11.2 changes no code at all**, so its
headline check is mechanical and a reviewer can settle it in one command:
*is every `crates/**/*.rs` change a doc comment or an inner doc attribute?*

**Publish order is `gmcrypto-simd` → `gmcrypto-core` → `gmcrypto-c`.** The
intra-workspace path-deps are pinned exactly (`=1.11.2`), so each crate must
be live on crates.io before the next resolves. All three publish even though
only `gmcrypto-core` changed materially: `gmcrypto-simd` is the whole point of
the release (its crates.io page was rendering the wrong README), and the
lockstep pin forces `gmcrypto-c` along regardless.

**`cargo publish` and the SSH-signed tag are the maintainer's authenticated
call, never the agent's.** The 1.11.0 publish was a recorded one-off
delegation, not a standing grant (CLAUDE.md, "Release state").

**What this release is, and why it needs a version at all.** crates.io
metadata and docs.rs renders are baked into a *published version*: editing the
repository changes nothing a visitor sees until the next publish. Everything
in this patch was already true in the repository at 1.11.1 and invisible to
anyone who had not cloned it. Five things drove it:

1. **The wrong crate was the front door.** A crates.io search for `sm4`
   returns `gmcrypto-simd` above `gmcrypto-core`. `gmcrypto-simd` set
   `readme = "../../README.md"`, so its page rendered the *workspace* README:
   an H1 reading `gm-crypto-rs`, three badges pointing at `gmcrypto-core`, and
   no sentence saying it is an internal `rlib` backend outside SemVer.
2. **Feature-gated API was unlabelled on docs.rs.** `all-features = true` had
   it documented but unbadged — zero occurrences of `stab portability` in the
   live 1.11.0 HTML. `sm4::gcm_streaming` and `sm2::key_exchange` named their
   gating feature in no rendered documentation at all.
3. **`html_root_url` was pinned at `1.0.0`** while the crate was at 1.11.1.
4. **No example on the docs.rs front page**, which opened by deferring to
   "the workspace `README.md`" — a bare prose reference to a file not on
   docs.rs.
5. **README staleness rendered on crates.io**, where the README *is* the
   landing page.

**Audience.** Everyone who reads a page; nobody who runs code. There is no
behavioural claim to verify, on any feature combination, on any architecture.

Use `BLOCK` (do not publish until fixed/deferred), `WARN` (publishable,
track), `INFO` (note only).

## 3. THE HEADLINE CHECK — no code changed

**(a) Every Rust change is a doc comment or an inner doc attribute.**

```bash
git diff v1.11.1..HEAD -- 'crates/**/*.rs' | grep -E '^[+-]' | grep -vE '^(\+\+\+|---)' | grep -vE '^[+-]\s*(//|/\*|\*)' | sort -u
```

Expected output — exactly these two lines and nothing else:

```
+#![cfg_attr(docsrs, feature(doc_cfg))]
-#![doc(html_root_url = "https://docs.rs/gmcrypto-core/1.0.0")]
```

Both are inner attributes on `gmcrypto-core/src/lib.rs`. The removal drops a
URL that was stale by eleven minor versions. The addition compiles to nothing
unless `--cfg docsrs` is set, and the only thing that sets it is
`[package.metadata.docs.rs] rustdoc-args` — verified in (c).

**(b) No file outside the expected set changed.**

```bash
git diff v1.11.1..HEAD --stat
```

Expect: three `Cargo.toml`s + the workspace one, `crates/gmcrypto-core/src/lib.rs`,
the three READMEs (root, `gmcrypto-c`, and the **new** `gmcrypto-simd` one),
`CHANGELOG.md`, `CLAUDE.md`, `docs/`. A change to any other `src` file is a
`BLOCK`.

**(c) The `docsrs` cfg is set from exactly one place, and it is not CI.**

```bash
grep -rn 'docsrs' crates/ .github/ | grep -v '^crates/gmcrypto-core/src/lib.rs'
```

Expect two hits, both in `crates/gmcrypto-core/Cargo.toml`: the
`rustdoc-args = ["--cfg", "docsrs"]` line and the comment above it.
**Any hit under `.github/` is a `BLOCK`** —
`api-stability.yml`'s `cargo doc` job runs on **stable** with
`RUSTDOCFLAGS: -D warnings`, and `#![feature(doc_cfg)]` behind that cfg would
fail to compile there.

**(d) The stable render is still clean — the gate as it stands today.**

```bash
RUSTDOCFLAGS="-D warnings -A rustdoc::private_intra_doc_links" \
  cargo doc --no-deps -p gmcrypto-core --features digest-traits,cipher-traits,sm4-bitsliced,sm4-bitsliced-simd,sm4-aead,sm4-xts,crypto-bigint-scalar,sm2-key-exchange,x509,tlcp,aead-traits
```

**(e) The badges actually render.** This is the one thing in the release that
cannot be observed after publish without republishing, so observe it now:

```bash
cargo +nightly rustdoc -p gmcrypto-core --all-features -- --cfg docsrs
grep -c 'stab portability' target/doc/gmcrypto_core/index.html   # expect ~101, must be > 0
grep -rhoE '<div class="stab portability">[^@]{0,80}' target/doc/gmcrypto_core/ | sed 's/<[^>]*>//g' | sort | uniq -c | sort -rn
```

Every gated feature must appear, including the compound gates
(`tlcp and x509` for `tlcp::chain`, `sm4-aead and aead-traits`). `doc_cfg` is
an **unstable** feature: if a future nightly moves it again the docs.rs build
for this version fails and the remedy is a republish, not a patch to a live
page. That is the accepted cost, recorded here so it is not rediscovered.

## 4. Build, test, lint, dependency policy

The full local gate from `CLAUDE.md` § Commands. Nothing here is expected to
move, and the value of running it is precisely that: a docs-only patch that
perturbs a build is not a docs-only patch.

```bash
cargo test --workspace
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
# ...plus each opt-in feature's own clippy pass (see CLAUDE.md)
cargo test -p gmcrypto-core --doc      # the new crate-root example runs here
cargo generate-lockfile && cargo deny --exclude-dev check
```

The crate-root example is deliberately written against **default features**,
so `cargo test --workspace` exercises it. An example that needed a feature
flag would be silently unrun.

## 5. MSRV reproducibility

```bash
cargo +1.85 build -p gmcrypto-core
cargo +1.85 build -p gmcrypto-core --features digest-traits,cipher-traits,sm4-bitsliced,sm4-bitsliced-simd,sm4-aead,sm4-xts,crypto-bigint-scalar,sm2-key-exchange,x509,tlcp,aead-traits
```

`#![cfg_attr(docsrs, feature(doc_cfg))]` on a stable MSRV toolchain is the

## 9. ECOSYSTEM §8 Gate #1 — the downstream compatibility gate

**Already run twice: `docs/v1.11.2-gate1-evidence.md` — PASS both times.** The
candidate of record is **`2557cbe`** (= `RELEASE_SHA`); the earlier run against
`d3af8bf` is kept in that file as the record of the presentation cut. #178
changed files under `crates/`, which is exactly the condition below, so the
gate was re-run rather than assumed to still attach.

Re-run again only if `crates/` or the workspace `Cargo.toml` change after
`2557cbe`:

```bash
git diff 2557cbe..HEAD --stat -- crates/ Cargo.toml    # expect empty
```

Read the evidence file's own preamble before treating the PASS as more than it
is. The gate exercises compilation and behaviour, and neither can move when no

without exception"; the release skipped because nothing could break is the one
that discovers the manifest key it broke.

## 10. CI status — three identities, one tree

Confirm the checks that ran, and *which* SHA they ran on. Note that `ci.yml`
carries a `paths-ignore` filter for docs-only pushes: a docs-heavy patch may

## 12. The publish sequence (only after GO)

Run from a checkout of the reviewed commit. The `cd` is inside the block on
purpose — the app's Run button executes in the current directory, and the
1.11.0 publish shipped `gmcrypto-simd` from the wrong checkout because the
target directory was named only in prose.

`RELEASE_SHA` is filled in below: **`2557cbe`**, the squash of #178. It is
**not** `49e8df3` (#175): that was the presentation cut, and #178 then added
the four module landing pages. Both are docs-only — the §3(a) headline check
returns the same two attribute lines at either SHA — so 1.11.2 ships the
later tree rather than leaving the module pages for a release behind it. `main`
may sit ahead of it by later docs commits — this runbook's own finalisation
is one. Block 1 checks the SHA out
explicitly and every later block re-asserts it, so the published tree is the
reviewed one regardless of where `main` has moved. **Do not publish from
`main`'s tip**, and expect a detached HEAD until you `git checkout main`
afterwards.
