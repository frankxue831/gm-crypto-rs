# v1.11.2 — ECOSYSTEM §8 Gate #1 evidence

`docs/ECOSYSTEM.md` §8 requires the `gmcrypto-envelope-lite` gate suite — at
current tip, in every feature configuration the crate ships, executed by its
scripted gate — to pass against every `gmcrypto-core` release candidate before
it ships. This file is that record for the **1.11.2** patch.

**Candidate of record: `0de98e2` — the last section of this file.
Result: PASS**, both phases, both feature configurations (`default` and
`--features aead`), 0 failures. No runtime or API incompatibility, so **no
migration note is required** before this release ships.

The gate ran **three times**. The first run is the presentation cut `d3af8bf`
(#175), kept below as the record. #178 added the four module landing pages
and #179 rewrote the README, de-jargoned the crate-level docs and moved every
doctest onto `?` — both doc comments only, but both touch files under
`crates/`, which is exactly the re-run condition
`docs/v1.11.2-release-review.md` §9 names — so the gate was re-run against
each folded tree rather than assumed to still attach.

`RELEASE_SHA` is **`0de98e2`** (squash of #179). The check that decides
whether a re-run is owed, `git diff <gated-sha> <RELEASE_SHA> --stat --
crates/ Cargo.toml`, is non-empty against `d3af8bf` and `2557cbe` — which is
why the re-runs exist — and empty against `0de98e2`.

All three runs below are the gate script's own output, unedited; the script fails
closed, so a recorded run is a passing run.

## Why these runs are nearly content-free, and why they ran anyway

1.11.2 changes no code: the entire `crates/**/*.rs` delta is two inner
attributes on `gmcrypto-core/src/lib.rs`, one of which expands to nothing
without `--cfg docsrs` — and that stays true at both gated SHAs, module
landing pages included (`docs/v1.11.2-release-review.md` §3). The envelope
therefore compiles a `gmcrypto-core` that is behaviour-identical to 1.11.1 in
every phase of both runs, and a PASS was the only possible outcome short of a
defect in something other than the crypto.

That is precisely the residual risk worth spending a gate run on. This patch
edits **four `Cargo.toml` files** — a `readme` key repointed, a
`[package.metadata.docs.rs]` section added, `homepage` removed workspace-wide
from `[workspace.package]` and from all three inheriting crates, and both
sibling pins moved to `=1.11.2`. A manifest is exactly the kind of thing that
compiles fine in its own workspace and fails to resolve from a downstream
`[patch]` override. §8 says "before every `gmcrypto-core` release, without
exception"; a release skipped because "nothing could break" is the one that
discovers the manifest key it broke.

The gate's own §2 phase re-runs the downstream boundary scan against the
patched tree, which is what proves no absolute path was written into the
export's `Cargo.toml` by the override — the failure mode
`docs/v1.11.0-gate1-evidence.md` §4 records.

## What this gate does and does not establish

It establishes that `gmcrypto-envelope-lite` 0.4.0 builds, lints, and passes
its full suite against this candidate in both configurations it ships. It does
**not** exercise `sm4-bitsliced-simd` — no envelope configuration enables it —
and it says nothing about the docs.rs render or the crates.io pages, which are
the actual subject of this release and are only observable after publish
(`docs/v1.11.2-release-review.md` §13).
