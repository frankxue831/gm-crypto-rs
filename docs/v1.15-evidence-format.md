# v1.15 evidence qualification interface

The offline helpers in `.github/scripts/v115_evidence.py` implement the
selection, output and capture-identity portions of the accepted
[numerical protocol](v1.15-protocol.md). They do not start a study, collect
measurements, authenticate an Actions download or activate a gate. The
capture producer in `.github/scripts/v115_capture.py` has a build-only
preflight workflow. The read-only collector preserves authenticated API responses and archives;
capture binding and complete-census replay are implemented. Scheduled capture
is integrated for the declared calibration interval, September 29 through
November 9, 2026 UTC; see the [readiness and date declaration](v1.15-calibration-freeze.md).
T0 remains unset.
All committed tests use synthetic data and dates.

## Census selection

`select_scheduled_jobs(jobs, start)` takes the complete Actions job census
and a UTC start date for the fixed 42-day interval. Each record carries
integer `run_id`, `job_id`, `run_attempt`, `event`, `started_at` and the exact
`feature_leg`. The sampling date is the UTC job-start date. Sort by timestamp,
run ID and job ID within that date/leg, selecting only the first scheduled
attempt with `run_attempt=1`, before examining capture validity or a verdict.
Return all supplied rows, including manual events, reruns, outside-window
jobs and later attempts. Do not substitute another job for a selected failure.

Missing ordering metadata in a scheduled first attempt, an unknown feature
identity inside the window, or duplicate job identity raises an error. A valid
UTC start outside the window is enough to retain an older unknown job name as
excluded descriptive evidence; the exact original job name stays in the report. The collector must retain that
unresolved census evidence and repair provenance before deriving a table;
catching the error and dropping the ambiguous record would violate selection.
A census with no job for a date/leg must still report that absence when the
full window is evaluated. These helpers cannot detect an omitted API page.

## Output qualification

`qualify_outputs(text, feature_leg=..., sample_budget=..., cpu=...)` preserves
signed tau, signed t, printed crop size and seed for each result. It requires
exactly five numbered passes with the exact compiled feature string, one
finite five-decimal tau and one preceding seed per required target/pass,
finite t/crop statistics, and negative-control magnitude strictly greater
than 1.0 in every pass. The declared budget is 100000; the selected crop's
rounded size is retained without substituting it for that declaration.

Required targets match the current nightly feature strata, including the
four demoted sentinels and the nonblocking noise twin. Nonrequired probe
results remain in the observations, including nonfinite tokens, but cannot
supply a required result. Duplicate or malformed required output is invalid,
even if the remaining values look complete. Existing bound breaches are
reported without making otherwise complete outputs invalid; the twin's
magnitude remains nonblocking. All medians use the signed five-decimal values,
not the rounded gate-summary lists.

`outputs_valid` concerns only output completeness, numerical validity and
liveness. The retained breach list is diagnostic until the enclosing capture
and sampling selection qualify; invalid evidence cannot reject a table.

## Frozen capture contract

`qualify_capture(job, frozen, capture, files)` combines those output checks
with byte-level identity checks. The caller first authenticates the Actions
run/job census and archive download, verifies the GitHub artifact digest,
and associates the artifact with its exact job. The function accepts the
archive's exact file bytes, not a caller-provided eligibility boolean.

The separately reviewed `frozen.identity_sha256_by_leg` maps each feature leg
to exact hashes of these six files:

| File | Frozen meaning |
|---|---|
| `source-manifest.json` | Canonical complete crypto/harness/build-input inventory |
| `Cargo.lock` | Exact research resolution already used for structural controls |
| `resolution.json` | Canonical resolved package/dependency/feature identity for this leg |
| `toolchain.json` | Full effective rustc, cargo and active-toolchain identities |
| `build-config.json` | Target triple, feature string, profile and compilation flags |
| `capture-source.py` | Exact reviewed capture implementation |

The producer retains each under `before/` and `after/`; both must match the
independently frozen bytes. The producer writes source inventory in the already frozen structural-control
format and other identity JSON as sorted, indented UTF-8 with a final newline.
Concrete expected hashes require review of the build-only preflight artifacts. Never learn expected identities from
the observation being qualified. Changed inputs remain explicitly ineligible.

The schema-1 capture record contains:

- `metadata`: run ID, job ID, attempt, checkout `head_sha`, feature leg, CPU,
  image version and kernel. The first five match the independent job census;
  environment labels must be present. Checkout identity is separate from the
  frozen source-input inventory, allowing compatible documentation commits.
- `files`: exact archive-relative filename → SHA-256 mapping, checked against
  every supplied byte buffer and the complete supplied inventory.
- `binary_before_sha256` and `binary_after_sha256`: both match retained
  `timing.bin`. Every process ledger entry names that same binary.
- `processes`: five ordered entries carrying pass number, declared sample
  budget 100000, exact compiled features and binary digest, with
  `status=completed` and integer `returncode=0` for every process. Complete
  output emitted before a process fails cannot make that process eligible.
- `status=finalized`, `final_snapshot_status=complete`, and a nonempty
  `final_snapshot_attempts` ledger with every attempt complete. Any failed or
  unfinished attempt permanently excludes the capture, even after inputs are
  restored and a later final snapshot succeeds.
- Retained `output.log`, containing the five numbered pass headers and outputs.

The capture producer must actually record those snapshots and process
identities at the declared boundaries. Hash agreement cannot authenticate an
arbitrary self-authored archive or prove that its named producer executed;
the collector also verifies the executed workflow/capture revision against
the reviewed freeze. A missing archive, partial upload, failed first draw or
incompatible build must remain in the census and exclusion table.

`capture_qualified` still does not establish selection, elapsed-window
completion, candidate/control coverage or final outcome. Consumers must
combine it with first-attempt selection and the numerical rules, preserve all
excluded observations, and apply the accepted whole-table outcome precedence.


## Producer and build-only preflight

`v115_capture.py prepare` verifies the existing structural-control lock and
129-file source manifest, effective Rust 1.95.0 and host triple, compilation
environment and absence of unfrozen external Cargo configuration. It retains
canonical package sources, resolved features and dependency edges, normalizing
only checkout paths of workspace packages. Registry sources and versions stay
literal. The metadata graph describes Cargo's workspace resolution; the complete
compiler-artifact stream is also retained to identify the actual bench build.

Preparation runs `cargo bench --no-run --locked` and saves the executable;
it never launches it. An existing different root lock is refused, not replaced
or regenerated. Build inputs are snapshotted before compilation and again
afterward. A preparation without `--freeze` is permanently marked build-only.
The preflight workflow uses this mode on all four feature legs, pins the
compiler and disables incremental compilation, records the Actions job via the
read-only API, and uploads complete or partial evidence. It has pull-request
path triggers and a manual trigger, with no schedule or timing execution step.
Its 15-minute build-only timeout does not change the production nightly budget.

`run-pass` additionally requires the exact freeze used during preparation,
all six frozen file identities, declared consecutive 42-day calibration dates,
an in-window UTC job start, `event=schedule`, attempt 1 and remaining time
within the existing 40-minute job limit, reserving 120 seconds for evidence
preservation/upload and five seconds for process termination. It refuses another
pass once the remaining measurement allowance reaches zero. It rechecks build identity before each
pass, records the attempt before launching the saved binary, forces 100000
samples and preserves partial output on failure or timeout. A failed, started
or already recorded pass cannot be retried in place. The producer emits the
original numbered nightly log files as well as the combined evidence log.

`finalize` records a started attempt before taking a fresh snapshot in a unique
attempt directory, checks the retained executable, then publishes the complete
final snapshot. Missing or failed finalization is ineligible even if earlier
`after/` files still match; starting another pass invalidates finalization. Failed
attempts retain their partial files and status. Post-build, pre-pass and final
metadata snapshots use Cargo offline mode. Finalization hashes all artifact
files except its own `capture.json` index. Preparation, execution
and finalization errors remain recorded; artifact absence after a runner-level
failure is still an explicit census exclusion. Before/after hashes bind these
records to a reviewed producer but do not replace authenticated artifact and
workflow provenance checks in the collector.

The current run-pass interface authorizes calibration only. Confirmation and
isolated-control execution require their own accepted candidate/T0 conditions
and scheduling integration. The code and synthetic tests do not declare C0/T0;
the scheduled calibration route uses the separately reviewed date declaration.


## Authenticated transport and census preservation

`.github/scripts/v115_collect.py --workflow <filename.yml> --output <new-directory>`
uses authenticated `gh api` GET requests to this repository on github.com. It
preserves the entire workflow history without event, date, conclusion or CPU
filters, including every numbered rerun attempt, its jobs, available raw log
archive, all artifact metadata and downloaded archive bytes. Missing/expired
logs and artifacts remain explicit. Authentication, permission, rate-limit and
server errors leave the collection incomplete; they are not classified as
missing measurements. A new output directory is required for each snapshot.

Every API page and byte archive is retained under a local `raw/` directory,
with request endpoints, fetch times and SHA-256 hashes in `collection.json`.
Artifact downloads must match GitHub's advertised SHA-256 and run/source
identity before receiving `status=verified`; missing hashes, mismatches and
invalid ZIPs remain recorded and unverified. ZIP inspection checks CRCs and
rejects duplicate/unsafe paths and symlinks without extracting any files or
executing their contents. Exact workflow and capture-source content responses
are retained at each run's source SHA, including explicit missing files. For
pull requests, this SHA is the API head and need not be the checkout merge
commit; these runs remain descriptive and cannot qualify as scheduled draws.

Pagination checks API counts and unique identities. A changed count, truncated
page, duplicate job or mismatched run/attempt identity leaves an incomplete
collection. A second run census rejects runs or rerun attempts added while
collecting. At 1000 workflow runs the collector refuses the snapshot because
the API's result cap requires a separately implemented partitioned census; it
must never silently truncate the study history. Failed snapshots stay on disk.

`status=complete` means the transport census was preserved, including explicit
evidence absences. It does not mean that every draw has usable evidence, that
a window has elapsed, or that captured output is eligible. An artifact digest
authenticates the downloaded bytes only. Before qualification, the consumer
must bind the exact scheduled job and artifact, compare the executed workflow
and producer to their independently reviewed freeze, and pass exact capture
bytes through `qualify_capture`. This transport unit does not perform that
binding, derive a table, set calibration dates, or launch a workflow.
Raw archives stay local; publication uses the protocol's redacted per-pass
and per-job records rather than publishing unrelated setup logs or host paths.

at reviewed producer revision `2820fec2c9670f8e80b42ebe30ca750139c7e804`,
merged as `3f1b6b1de2738c428cd6248556d525c907faa25c`. All four jobs
completed without timing execution. Four GitHub archive digests, 60 captured

[preflight](https://github.com/frankxue831/gm-crypto-rs/actions/runs/36441179293)
is also preserved; its producer bytes are superseded and do not define

The build manifest records build-only qualification; its C0 and T0 fields
remain null. The separate execution freeze adds the reviewed scheduled workflow
digest, workflow ID, exact four job names and declared calibration dates. A canonical JSON execution freeze must be
retained as `v115-capture/freeze.json` in each eventual study artifact.

`v115_capture_binding.bind_capture` consumes authenticated attempt/job records,
the complete run artifact listing, exact archive bytes and source contents
retrieved at the API source SHA. It requires a first scheduled attempt on
this repository's main branch, the frozen workflow ID/path and exact workflow
and producer content hashes. The complete, unambiguous frozen job-name map
identifies feature strata before capture qualification. Unknown job strata
raise an unresolved census error rather than silently disappearing.

Exactly one artifact named `v115-capture-<job_id>` must match its API run,
source SHA and advertised digest. Capture event/start time match the API job,
and retained freeze bytes match the independently reviewed execution freeze.
Only then can the archive's capture pass the existing byte-level qualifier.
Missing, duplicate, expired, drifted and malformed evidence returns explicit
issues; any parsed observations remain available with their eligibility status.
The workflow's conclusion is not a success filter: a complete capture can
contain a valid existing-threshold breach that made the gate step fail.
Every measurement process itself must have completed successfully.

This binding function does not reconstruct a missing census, authenticate
caller-invented API objects, establish first-date selection, or prove window
completion. Its caller must retain the collector's complete authenticated
provenance, select first attempts before inspecting validity, and apply fixed
window and coverage rules. No new workflow, timing run or gate change is
introduced by these build records and binding helpers.


## Complete-census calibration replay

`v115_replay.py` replays a preserved collector snapshot without network access
or executing downloaded content. It checks every raw file hash and replays
every request, in order, through the same collector checks. Reconstructed run,
attempt, job, artifact and source indexes must exactly match the saved index;
missing pages, omitted requests, changed indexes and unconsumed bytes fail
closed. This detects local inconsistency, not forgery of a whole caller-invented
collection; the input must come from authenticated collection.

The calibration report requires the complete reviewed execution freeze,
including the exact 42-day interval. It calls first-attempt selection on the
whole job census before inspecting archives. Invalid first draws remain
selected and cannot be replaced by later successes. Manual and rerun evidence
stays excluded. Unknown in-window scheduled strata or missing ordering metadata halt
derivation as unresolved census evidence. Older job names with unambiguous
outside-window timestamps remain in the report as excluded rows. Zero-job attempts remain explicit.

For each selected, bound and qualified capture, the report retains exact signed
per-pass values, environment identities and existing-gate breaches. It fits the
four demoted targets only, by exact feature-leg/normalized-CPU cells, using the
accepted decision kernel. Cells observed only in excluded draws remain visible
with zero eligible dates. Unknown CPU fallbacks and unchanged fanout policy
remain explicit. Missing draws are listed for every one of the 168 date/leg
slots. Existing-gate failures are preserved rather than filtered by job success.

No numerical candidate is derived while the snapshot predates the exclusive
endpoint or any selected job is still running. After the full interval, a
nonempty proposed set requires candidate review; an empty set records
`insufficient evidence` for a new table. Neither status authorizes activation,
changes an endpoint or starts confirmation. Remaining investigation findings
still belong in the completed study report.

The CLI writes a new local output directory containing `calibration.json`,
`passes.csv`, `jobs.csv` and `exclusions.csv`. The JSON includes the source
collection and freeze digests, exact extractor-script hashes, environment
manifest, every observed cell, fallbacks and the proposed set. Replaying the
same snapshot with the same scripts and freeze after completion produces the
same report. These files require disclosure review before publication; raw
archives and malformed source lines remain local evidence. The CLI has no
activation command and refuses to overwrite an existing output directory.


## Scheduled integration and declared calibration window

The [execution freeze](v1.15-execution-freeze.json) combines the verified build
identities with the nightly workflow ID, exact source hash and four job names.
The integration was merged with both calibration dates null, preserving the
ordinary nightly loop. The separate [declaration](v1.15-calibration-freeze.md)
sets C0 to September 29, 2026 at 00:00 UTC and the exclusive endpoint to
November 10 at 00:00 UTC after the readiness audit. One missing date, malformed
dates or a non-42-day interval is an error. T0 remains unset.

The nightly producer verifies the exact SHA-256 of `v115_nightly.py` before
running it. This literal checksum is part of the independently frozen workflow
bytes, so the capture binder's workflow hash also binds the orchestration
helper. The helper uses only standard-library imports and invokes the exact
reviewed capture producer, whose bytes are checked before execution. The
assurance checker pins helper bytes and the complete shell route, and mutation
tests reject checksum removal, swallowed routing failure, capture bypass,
unreviewed freeze paths, write permissions and loss of failure-time uploads.
The existing gate-parser AST, thresholds and PR-smoke policy are unchanged.

For declared calibration windows, only first scheduled attempts can take the
capture path. The helper resolves the API run and exact job name, verifies
checkout and workflow identities, and uses the actual UTC job-start date.
Manual events, reruns and outside-window jobs keep the ordinary loop. A matching
in-window draw that encounters source or capture drift fails; it cannot fall
back to another unrecorded measurement. Metadata routing was checked against
all four archived jobs in scheduled run 35185121870 without launching timing.

The capture path downloads the exact previously frozen research lock, verifies
its digest, builds with incremental compilation disabled, and invokes the
existing producer's five sequential passes. A failed pass stops the sequence
and is never retried. Finalization runs in cleanup whenever a capture index
exists. Job timeout remains 40 minutes and each pass retains the producer's
125-second termination/preservation reserve. Existing parser logs and gates
remain in place. A job-specific capture archive uploads under `always()` with
90-day retention, including partial evidence and provenance when preparation
or measurement fails; the existing raw-log upload remains unchanged.

The four-leg build-only preflight also exercises routing and asserts that
PR/manual preflight cannot select study measurement. It still prepares without
a freeze, leaves measurement disabled, and runs no timing binary. Its separate
15-minute build limit does not change the production measurement budget.
