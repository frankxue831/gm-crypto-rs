# v1.16 scope — GFNI SM4 S-box behind `sbox_x32`

**Status:** **draft, 2026-09-29.** Direction approved by the maintainer
on 2026-09-29: GFNI at AVX2 width (Q16.1), a compiler-version-gated build
that keeps MSRV 1.85 (Q16.2), and an Intel SDE CI job plus native tests
(Q16.4). Mirrors `docs/v1.13-scope.md` (why-now → structural facts → forks
Q16.x with a recommendation each → assurance → risks → out of scope →
sequence).

One item, **performance-only**, no public API change: when the host CPU has
GFNI, `gmcrypto_simd::sm4::sbox_x32` computes its 32 S-box bytes with two
GFNI instructions instead of the AVX2 bitsliced gate sequence. This closes
the long-deferred "AVX-512 `sbox_x64`" backlog item (first recorded as
v0.5 Q5.12) by replacing its premise; see Q16.1.

**Merge window.** This touches `crates/`, which the v1.15 calibration
freezes (`docs/v1.15-calibration-freeze.md`). The branch and its PR may be
built and reviewed at any time. The merge waits until the freeze lifts:
after 2026-11-10, or after the v1.15 confirmation window if the
calibration yields a nonempty candidate set. Release is by the next
publishing cycle, gated by `docs/ECOSYSTEM.md` §8.

---

## 1. Why now

The AVX-512 `sbox_x64` item has been carried forward since v0.5 with two
stated blockers: no AVX-512 host to develop on (the maintainer host is
AArch64), and no evidence the gain was worth a 16-block core batch. Both
premises have moved:

- GitHub's hosted `ubuntu-24.04` pool now includes EPYC 9V74, EPYC 9V45,
  Xeon Platinum 8573C and Xeon 6973P-C, all with GFNI and AVX-512
  (`docs/v1.15-nightly-corpus.csv`). Intel SDE removes the host problem
  for correctness testing entirely (Q16.4).
- GFNI computes an arbitrary GF(2^8)-inverse-plus-affine S-box in two
  instructions per byte. The SM4 S-box is exactly that shape, so the
  win comes from the instruction, not from register width. That lets
  the change stay inside the existing 32-byte `sbox_x32` shape, with no
  change to core's `SIMD_BATCH` or to the `ct_sm4_cbc_decrypt_fanout`
  dudect window.

## 2. Structural facts

- `sbox_x32` is the only full-batch S-box on `x86_64`. Core reaches it
  under `sm4-bitsliced-simd` through `Sm4Cipher::encrypt_blocks` /
  `decrypt_blocks` and the batch round loop in `cipher.rs`
  (`SIMD_BATCH = 8` on `x86_64`), which serve the CBC-decrypt fanout
  (`cbc_streaming.rs`) and the CTR keystream (`ctr_streaming.rs`), and
  through CTR the GCM and CCM paths. Today it dispatches AVX2
  (`sbox_x32_avx2`) else scalar.
- `sbox_x4` (single block, key schedule) stays four scalar calls on
  `x86_64`; the 10% rule in `docs/sm4-single-block-simd-repair-design.md`
  was unmeasured for AVX2. Out of scope here (§7).
- The SM4 S-box is `S(x) = A·inv(A·x ⊕ B) ⊕ B` over
  `p(x) = x⁸+x⁷+x⁶+x⁵+x⁴+x²+1` (`0x1F5`), `A` the circulant of `0xD3`,
  `B = 0xD3` (`crates/gmcrypto-simd/src/sm4/scalar.rs`).
- GFNI's `GF2P8AFFINEINVQB` inverts in the AES field (`0x11B`). With a
  field isomorphism `T: GF(2^8)/0x1F5 → GF(2^8)/0x11B`:
  `y = GF2P8AFFINEQB(x, T·A, T(B))`, then
  `S(x) = GF2P8AFFINEINVQB(y, A·T⁻¹, B)`. All eight choices of `T`
  (one per root of `p` in the AES field) reproduce the SM4 table for all
  256 inputs in an offline model. That model encodes the instruction's
  matrix byte order from the Intel SDM; the exhaustive Rust test under
  SDE (Q16.4) is the binding check, not the model.
- `gfni`, `vaes`, `vpclmulqdq` and the `avx512*` target features were
  stabilized together in Rust 1.89.0 (rust-lang/rust#138940). The
  workspace MSRV is 1.85, where they are unstable.
- `cpufeatures 0.2.17` detects `gfni`, but classifies it with the
  `zmm` state check, so it reports `false` on CPUs with GFNI but no
  OS-enabled AVX-512 state (for example Alder Lake desktop parts). This
  is a safe false negative: those CPUs keep today's AVX2 path.

## 3. Forks

### Q16.1 — What to build: GFNI at AVX2 width *(decided 2026-09-29)*

Options were: (a) GFNI inside `sbox_x32` at 256-bit width; (b) the literal
16-way bitsliced `sbox_x64` with a 16-block core batch on AVX-512; (c) GFNI
at 512-bit with a 16-block batch; (d) close the item as not worth doing.

**Decision: (a).** Largest expected gain per unit of blast radius: no core
change, no change to `SIMD_BATCH`, no change to what the fanout dudect
target measures structurally. (b) doubles width of a gate sequence that
Zen 4 splits into two 256-bit halves anyway, and makes the fanout batch
size CPU-dependent. (c) is a possible later cycle, once (a) is measured.

### Q16.2 — MSRV: version-gated build *(decided 2026-09-29)*

A `build.rs` in `gmcrypto-simd`, with no build dependencies, runs
`$RUSTC -V`, parses `major.minor`, and on `>= 1.89` emits
`cargo::rustc-cfg=gmcrypto_simd_gfni`. It always emits
`cargo::rustc-check-cfg=cfg(gmcrypto_simd_gfni)` and
`cargo::rerun-if-env-changed=RUSTC`. An unparseable version string omits
the cfg (fail closed to today's code), never fails the build.

All GFNI code sits behind
`#[cfg(all(target_arch = "x86_64", gmcrypto_simd_gfni))]`. On 1.85–1.88
the crate compiles exactly today's code. The existing `+1.85` MSRV job
runs on aarch64, where `target_arch` already excludes the GFNI code, so
`simd-x86` gains an x86_64 `cargo +1.85 build` of `gmcrypto-simd` and of
core with `sm4-bitsliced-simd,sm4-aead` (review item, 2026-09-29). A 1.89
pre-release fails closed (early 1.89 nightlies predate the
stabilization). MSRV stays 1.85; CLAUDE.md's MSRV line gains one
sentence that the GFNI path needs 1.89 and is compiled out below it.

Rejected: raising MSRV to 1.89 (changes a published 1.x crate's
supported-compiler contract for a performance item); nightly-only opt-in
(almost no user would get the speedup).

### Q16.3 — Dispatch and detection

`detect.rs` gains `has_gfni_avx2()` via
`cpufeatures::new!(cpuid_gfni_avx2, "gfni", "avx2")`, cached like
`has_avx2()`, compile-time `false` off `x86_64` or without the cfg.
`#[doc(hidden)]` re-export beside `has_avx2`.

`sbox_x32` order: GFNI+AVX2 if detected and selected (Q16.5) → AVX2
bitsliced → scalar. New `#[doc(hidden)] pub unsafe fn sbox_x32_gfni`
with `#[target_feature(enable = "gfni,avx2")]`, one load,
`_mm256_gf2p8affine_epi64_epi8`, `_mm256_gf2p8affineinv_epi64_epi8`, one
store. The two matrices and constants are `const` in a new
`sm4/gfni.rs`, each with a comment giving its derivation. `// SAFETY:`
at the dispatch site names the `has_gfni_avx2()` precondition, as today.

**Recommendation:** as written. No detection inside core; core still
calls `sbox_x32` unchanged (`.claude/rules/simd.md`).

### Q16.4 — Correctness evidence *(decided 2026-09-29)*

1. **Constants are derived, not trusted.** A test builds `T` from the
   field definitions (a root of `p` in the AES field), composes the two
   affine matrices, encodes them in the instruction's byte order, and
   asserts equality with the `const` values.
2. **Exhaustive equivalence.** Every byte value in every one of the 32
   lane positions matches `scalar::sbox_byte`, following
   `tests/lane_position_x32.rs`. Runs natively whenever GFNI is detected.
3. **Intel SDE job.** A new `ci.yml` job on `ubuntu-24.04` downloads a
   pinned SDE release, verifies its SHA-256 before extraction, and runs
   `cargo test -p gmcrypto-simd` with
   `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUNNER="sde64 -spr --"`
   (Sapphire Rapids: GFNI + AVX-512). It sets
   `GMCRYPTO_SIMD_EXPECT_GFNI=1`, which makes a test assert
   `has_gfni_avx2()` is `true`, so the job cannot silently pass on the
   fallback. Actions are referenced the same way as the rest of
   `ci.yml`; only the SDE archive itself is hash-pinned.
4. **Both compiler sides.** Stable CI compiles the x86_64 GFNI path
   with `-D warnings` (`simd-x86`); the same job's x86_64 `+1.85` build
   proves the gated-out side. No job runs clippy on x86_64: enabling it
   surfaced 19 pre-existing lint errors in the AVX2/CLMUL code, left to a
   separate change. A unit test of the build script's version
   parser covers `1.85.0`, `1.89.0`, 1.89 pre-releases,
   `1.97.0-nightly` and unparseable strings.

### Q16.5 — Adoption: the 10% rule applies

Following `docs/sm4-single-block-simd-repair-design.md`, the GFNI branch
becomes the production branch of `sbox_x32` only if, on the same GFNI
host, its repeated median (at least five samples) is at least 10% faster
than `sbox_x32_avx2` for both the CBC-decrypt 8-block batch path and CTR
keystream at 1 KiB and 256 KiB. SDE timings never count.

Measurement runs from a never-merge research branch workflow on hosted
`ubuntu-24.04`, dispatched until it lands on a GFNI SKU, with the
`RUNNER-CPU:` line and `rustc -Vv` recorded. The harness stays outside
the repository; the selection record (date, CPU model, rustc, medians,
outcome) is committed as a comment above the dispatch branch, like the
x4 precedent. If the rule is unmet or unmeasured, `sbox_x32_gfni` stays
a tested candidate that `sbox_x32` does not call.

**Recommendation:** as written.

**Result (2026-09-29): met; GFNI selected.** Of three dispatched runs, two
landed on EPYC 7763 (no GFNI) and measured nothing; run 36651586704 landed
on AMD EPYC 9V45 (rustc 1.98.1). Medians of five alternating samples:
`sbox_x32` 173.46 ns (AVX2) vs 7.26 ns (GFNI); `encrypt_blocks` and
`decrypt_blocks` at 1 KiB and 256 KiB 21.9–22.0 MB/s vs 226.7–230.8 MB/s,
about 10x in every case. The full record sits above `sbox_x32`. No Intel
GFNI SKU was measured; the rule needs one host, and the gap leaves no
plausible reversal on another.

### Q16.6 — Constant-time posture

The GFNI path has no table lookups and no data-dependent branches. Two
items must be confirmed before merge and recorded in the PR, not assumed:

- `GF2P8AFFINEQB` and `GF2P8AFFINEINVQB` appear on Intel's
  Data Operand Independent Timing instruction list, and AMD documents no
  data-dependent timing for them on Zen 4 / Zen 5.
- The PR-smoke dudect run and one dispatched nightly show the
  `ct_sm4_cbc_decrypt_fanout` target within its current bounds on a
  runner whose `RUNNER-CPU:` has GFNI. That target now exercises the new
  path on GFNI SKUs and the old one on EPYC 7763; the bounds, including
  the 9V74-only 0.55 `SKU-GATE`, do not change in this cycle.

**Status (2026-09-29).** Intel's
[Data Operand Independent Timing Instructions](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/resources/data-operand-independent-timing-instructions.html)
list (updated 2026-02-23) includes both `GF2P8AFFINEQB` and
`GF2P8AFFINEINVQB`; Intel's usual limits apply (DOIT behavior, not power or
frequency channels), as they already do for the AVX2 path. No AMD
instruction-level equivalent was found, so on Zen 4 / Zen 5 the dudect
evidence in the second bullet is the only check. The construction matches
published constant-time GFNI SM4 work (IACR ePrint 2022/1154).

**Dudect (2026-09-29, corrected 2026-09-30), with GFNI selected (commit
`17c97c6`).** The CPU model string does not identify the path: hosted
**EPYC 9V74 VMs come in two kinds**, some exposing GFNI and AVX-512 to the
guest (`lscpu` Flags) and some exposing neither. The job's `lscpu` Flags
line, not `RUNNER-CPU:`, decides which `sbox_x32` branch ran.

- Dispatched nightly run 36651973222 (manual, so outside the v1.15
  cohort), `sm4-bitsliced-simd` leg on an EPYC 9V74 **with `gfni` and
  `avx512f` in its Flags**: `ct_sm4_cbc_decrypt_fanout` median |tau|
  **0.0083** (100K×5). This is the GFNI-path evidence. The EPYC 7763
  (AVX2) leg read 0.0242; all legs green.
- PR smoke run 36651954457, `sm4-bitsliced-simd` leg on an EPYC 9V74
  **without** `gfni` in its Flags: 0.0594 (10K×3). This measured the AVX2
  path; it was first recorded here as GFNI evidence in error.

One GFNI-path dudect reading so far. Logging the selected branch in the
harness would remove the inference; it needs a dudect harness change,
deferred past the v1.15 freeze.

## 5. Risks

- **Matrix byte order wrong.** Caught by the exhaustive test under SDE on
  the first CI run; the derived-constant test pins the encoding rule.
- **SDE download is a third-party binary in CI.** Pinned version and
  SHA-256, test job only, no secrets in that job, never on release paths.
- **cpufeatures false negatives** leave some GFNI CPUs on AVX2. Safe;
  revisit only if a user asks.
- **CPU-dependent dudect behavior** in the fanout target (GFNI vs AVX2 by
  SKU). Already the case today between AVX2 SKUs; Q16.6 requires
  evidence on a GFNI SKU before merge.
- **Merge timing** is bound to the v1.15 freeze; the branch may need a
  rebase if `main` moves in unfrozen paths meanwhile.

## 7. Out of scope

512-bit width and 16-block batches, VAES/AES-NI SM4 tricks, any core
change, any dudect bound change, MSRV change.

**Follow-up taken (2026-09-30): `sbox_x4` via GFNI.** First listed here as
out of scope; built on a branch stacked on this one. `sbox_x4_gfni` moves
the four bytes through one 128-bit register (`_mm_cvtsi32_si128`, no
memory staging) and `gfni::sbox_round_128`, the 128-bit form of the same
two instructions and constants. Under the x4 10% rule (both key
construction and pre-keyed single-block encryption) on a hosted Intel
Xeon 6973P-C, rustc 1.98.1: key construction 11939.6 → 171.9 ns and
single block 11640.9 → 191.8 ns (medians of five, ~60x); selected. Five
of six dispatched runs drew no GFNI-exposing runner (EPYC 7763, or 9V74
VMs without `gfni` in their flags).
