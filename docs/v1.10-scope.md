## Q10.1 — The blocking discovery: the gmssl oracle had already drifted

Scoping W1 turned up something that reframes it. The maintainer's
`/opt/homebrew/bin/gmssl` is **GmSSL 3.2.0**, and 3.2.0 renamed the subcommands
the interop suite invokes:

| suite invoked | 3.2.0 |
|---|---|
| `pbkdf2` | renamed `sm3_pbkdf2` |
| `sm4 -cbc` / `-ctr` / `-gcm` | split into `sm4_cbc` / `sm4_ctr` / `sm4_gcm` |
| `sm3hmac`, `sm2sign`, `sm2verify`, `sm2encrypt`, `sm2decrypt` | unchanged |

Every affected call site asserts on exit status, so
`GMCRYPTO_GMSSL=1 cargo test --test interop_gmssl` failed **5 of 11** default
tests (7 of 13 under `sm4-aead`). **The "11/11 interop" claim in `README.md` was
not reproducible on the maintainer's own machine.**

That changes F16's character. The audit framed it as an either/or — wire gmssl
into CI **or** relabel the claim as maintainer-verified — and the relabel branch
had already shipped in `afd9bd1`. But a maintainer-verified claim that the
maintainer cannot reproduce is worth nothing. CI is now the only thing that
keeps the claim true, so the "wire it in" branch is taken.

## Q10.2 — Oracle version: pin **v3.2.0**, migrate the suite

**Decision: v3.2.0.** Two facts made this cheap and made 3.1.1 unattractive:

- The migration is a **pure subcommand rename**. Every option flag
  (`-encrypt`/`-decrypt`, `-key`, `-iv`, `-in`, `-out`, `-pass`, `-salt`,
  `-iter`, `-outlen`, `-aad`) is byte-identical across the two releases.
- 3.2.0 is what `brew install gmssl` gives you today. Pinning 3.1.1 would mean
  the suite could not be run locally without a hand-built binary, and the oracle
  would drift further from upstream every year.

Rejected: a **version-adaptive** suite that detects the reported version and
dispatches. It adds branching to the one component whose job is to be a
trustworthy oracle, and doubles the surface that can silently rot.

### Two behavioral changes, not just a rename

The plan flagged four comments recording behavior verified against 3.1.1. All
four were re-checked; two had changed:

- **`sm3hmac` now accepts keys of 12..=32 bytes only.** The upper bound is
  unchanged; the **12-byte lower bound is new** (measured: 11 rejects, 12
  accepts) and it rejected the RFC-style 4-byte `"Jefe"` and empty-key vectors,
  which abort inside `sm3_digest_init()`. Both paths — and the long-key
  hash-first path, never CLI-reachable — are already covered by in-tree KATs in
  `src/hmac.rs::tests`. The cross-check now spans gmssl's admissible window and
  sits **exactly on both boundaries**, so a future narrowing fails loudly rather
  than silently shrinking what the oracle checks.
- **`sm3_pbkdf2` rejects iteration counts below 10 000** (measured: 9 999
  rejects, 10 000 accepts). The doc comment claimed `<1000` while the inline
  comment claimed `<10000` — they contradicted each other and the doc one was
  wrong. Both now carry the measured bound.

Still true in 3.2.0, re-verified: `-iv` **is** the initial CTR counter block,
and `sm4_gcm` accepts arbitrary IV lengths (8/12/16/24 checked).

## Q10.3 — CI shape

**A new job inside `ci.yml`, not a standalone workflow.** `ci.yml` deliberately
carries no `paths` filter on `pull_request`, so it reports on every PR and can
later be made a required check. A standalone file with a `paths:` filter would
recreate the #90/#91 permanent-"Expected" trap that `fuzz-build.yml` still lives
with.

**`ubuntu-24.04`, OS label pinned.** A from-source build's reproducibility rides
the runner's compiler. This is *not* the dudect calibration pin — no `|tau|` is
at stake — but the same discipline costs nothing.

**Running x86_64 while the maintainer's oracle is aarch64 is deliberate.** Two
independent instances of the reference implementation agreeing is stronger
evidence than one. Confirmed on the first run: both builds agree on every wire
vector.

Four details that are load-bearing rather than stylistic:

1. **`-DBUILD_SHARED_LIBS=OFF`.** Upstream defaults it **ON**, which yields a
   binary linked against `@rpath/libgmssl` (confirmed via `otool -L` on the
   local build). A cached dynamic build would restore un-runnable.
2. **The cache key carries the tag AND a hand-bumped `GMSSL_CACHE_EPOCH`**,
   because changing the cmake flags does not move the tag.
3. **No `restore-keys`.** A fuzzy restore is exactly how a run goes green
   against the wrong oracle.
4. **A mandatory silent-skip guard.** The suite passes when `GMCRYPTO_GMSSL` is
   unset, so a variable that failed to reach the test process would show 13
   green tests that ran nothing — the same bug class as the missing seeds dir
   that mis-reported 44 consecutive nightly runs as CRASH. The step greps for
   `skipping: GMCRYPTO_GMSSL` and fails.

**Non-gating on landing** (`continue-on-error: true`). A third-party source build
is a new failure surface — upstream availability, cmake drift on the image,
cache eviction — and requiring it on day one would let any of those block every
PR in the repo. Same posture `cargo-semver-checks` had until #86. **Flip to
enforced** in a follow-up once it has a green track record; that flip, and
adding it to branch protection, is a maintainer action.

First run: built in ~17 s, `oracle: GmSSL 3.2.0`, 13/13.

## Q10.4 — F21: the audit's suggested class-split axis is refuted

The CT-discipline audit suggested class-splitting `ct_sm4_cbc_unpad` on **pad
validity**. That is wrong, and not marginally: a validity split makes one class
return `Some(Vec<u8>)` and the other `None` — different downstream work, not one
branch. It would measure the API's *shape*, and the deliberate one-bit leak
`mode_cbc`'s module doc already names, rather than the masked scan's discipline.

**Replacement axis: two VALID pad lengths (1 vs 16), fixed key/IV, equal 32-byte
ciphertext, both classes succeeding** — the house shape used by
`ct_pkcs8_decrypt`, `ct_sm4_gcm_decrypt` and `ct_sm2_key_exchange`. The closest
structural precedent is **`ct_tlcp_cbc_deprotect`**: fixed key, equal wire
length, class-split by a length-like secret, gated at 0.20 and never demoted.

**The two plaintexts share their first 16 bytes**, so CBC ciphertext block 0 is
byte-identical across classes and only the final block carries the class label —
the smallest two-input delta this shape admits. That matters because all four
demoted targets were demoted for two-input class-split runner noise.

**Timed window: the full `mode_cbc::decrypt` at 32 bytes.** Not the strip alone —
`strip_pkcs7_ct` is private, so reaching it would need a `#[doc(hidden)] pub`,
an API change for a bench-only reason. Not 256 bytes either: a constant-time
prefix leaves the class mean difference unchanged but grows the variance,
shrinking `tau` against an *absolute* 0.20 gate, and a ~15-iteration
control-flow regression is ~1 % of a 256-byte window. The harness's own v0.1
precedent records a `|tau| ≈ 0.70` leak diluting to 0.04–0.14 inside a
composite — quiet *and blind*. 32 bytes is the smallest window that still
behaves like a composite.

**Not cfg-gated** (`mode_cbc` is always-on), so the target appears in all four
matrix legs. Worth stating plainly: the only current indirect coverage,
`ct_sm4_cbc_decrypt_fanout`, is cfg-gated on `sm4-bitsliced-simd` **and** uses a
block-multiple plaintext, so `pad_len` is 16 in both of its classes. **There is
no pad-length class coverage anywhere today.**

### Q10.5 — Q18.7 is necessary but not sufficient

Q18.7 is a **quietness** bar (median < 0.15, ≤1 of 5 raw > 0.20, none > 0.40).
Every previously added target answered "does it detect a leak?" by construction,
because the split was by *key* and a key-dependent leak in a crypto primitive is
large. Here the split is by pad length and the leak signature is a small
control-flow difference, so passing Q18.7 would prove the target is quiet and
**nothing about whether it fires**.

**Mandatory pre-dispatch step: a sensitivity control.** In a scratch worktree,
replace the masked loop with an early-`break` loop (functionally identical,
timing-leaky), run at 100 K, and record the leaky `|tau|`. Nothing is committed.
This is `negative_control`'s philosophy applied to a new target — the leg Q18.7
does not have. Three green nightlies on a blind target is worse than no target,
because it buys a false sense of coverage.

### Q10.6 — Outcomes committed IN ADVANCE

Written down before the first dispatch, so a null result cannot retroactively
become "widen the window until it goes green". **All three are acceptable
outcomes of this cycle:**

1. **Clean promotion** — Q18.7 and the sensitivity control both hold → move into
   the unconditional `required_low` at 0.20 in a later cycle.
2. **Quiet but blind** — fails the sensitivity control → document the negative
   and **stop**. Do not widen the window to rescue it.
3. **Too noisy on the shared runner** → permanent telemetry, documented
   alongside the other four demotions.

Promotion is explicitly **a later cycle**, never this one.

### Q10.7 — Dedupe the unpad first

`mode_cbc.rs::strip_pkcs7_ct` and `cbc_streaming.rs::strip_pkcs7_block` are two
byte-identical private copies of the same masked scan (the latter's own comment
says so). A dudect target can only reach one of them, and someone "optimizing"
the streaming copy with an early return would stay functionally identical — the
fuzz differential stays green, the new dudect target stays green, and the
streaming path leaks.

**Decision: collapse to one `pub(crate)` helper.** `pub(crate)` is invisible to
both `cargo-public-api` and `cargo-semver-checks`, so no baseline drift; the v1.7
`sm3::compress` widening is direct precedent. This does edit constant-time source
inside a cycle otherwise framed as assurance-only — but a duplicated
constant-time primitive is exactly what an assurance cycle should be allowed to
collapse. Rejected: adding a second dudect target, which would double the
completeness surface and nightly runtime before the *first* unpad target has
proven promotable.

## Q10.8 — W3: the fuzz audit is 8 weeks stale

**6 of its 11 Tier-A rows already shipped** in #98/#99 (2026-06-09) — the
SM4-CBC / -XTS / -CCM / -GCM(16-byte-tag) roundtrips, the CBC streaming-encrypt
differential, and the GCM streaming-encrypt differential — while the doc still
shows them unchecked. The audit is a **dated receipt**: it gets a dated `Status`
addendum, never an edit to its checkbox rows.

**Live remainder: 4 upgrades + 2 new targets.** Census 30 → 32.

**The "no `PartialEq`" blocker dissolves.** Assert `encode(decode(x)) == x` on
`Vec<u8>`: no derives needed, and strictly stronger than value equality for a
canonical codec. Safe here because the codec is strict-canonical in both
directions — `reader.rs` rejects every non-minimal length form and every
non-canonical INTEGER, `writer.rs` emits only the minimal form, and every
decoder rejects trailing bytes. **Adding a derive to a published type for a
fuzz-only reason is explicitly out of bounds** (api-baseline drift).

Two corrections to the audit worth recording, both surfaced during scoping:

- **`decrypt_with_tag_len` is already fuzzed** (`fuzz_sm4_gcm_decrypt.rs:38`), so
  the "GCM × 7 tag lengths" row is narrower than written. The real gap is that
  `encrypt_with_tag_len` is reachable from no target and there is no round-trip
  at a truncated length. And "truncated == `full_tag[..t]`" is a **tautology** of
  the current implementation (it delegates to `encrypt` and truncates), so it is
  kept as a delegation-contract pin but labelled as such; the genuine invariant
  is the round-trip, because `decrypt_with_tag_len` recomputes `h`/`j0`/GHASH/
  GCTR independently rather than calling `decrypt`.
- **The "XTS sectors differential" row is partly duplicated** by
  `tests/sm4_xts_sectors.rs:73`, which already pins 36 shapes deterministically.
  By the audit's own Tier-B definition ("breadth over an invariant a
  deterministic unit test already asserts") it is Tier B. The genuinely new
  fuzz-only reach — arbitrary `start_sector` to the u128 ceiling, arbitrary
  key/buffer content, buf-untouched-on-`None` — must be stated in the target's
  doc-comment, or a reader concludes it is redundant.

Deliberately out of scope: **`sec1`** (its `decode` treats `[0] parameters` as
OPTIONAL while `encode` always emits it, so byte-idempotence is flaky *by
construction* — the audit's own §3 demotion is confirmed by source) and
**`pkcs8`** (handles live secret material under zeroize discipline).
`decode_c1c2c3_legacy` gets a differential rather than a round-trip, because
`encode_c1c2c3_legacy` does not exist **by design**.
