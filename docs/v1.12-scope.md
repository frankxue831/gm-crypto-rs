## 1. Why now

"SM4-CCM buffered input" has sat on the deferred list since v0.9 (§5 of
`docs/v0.9-scope.md`, re-deferred at v0.10 Q10.2), and the v0.15 cycle
(Q15.11) recorded the reason it stayed there:

> An "incremental-input" CCM API could only *buffer* the whole message and
> process it at finalize — **zero** memory benefit over the single-shot, a
> misleading "streaming" name, and a permanent SemVer surface for a
> non-feature.

That verdict is correct for the design it evaluated — one that lets the caller
feed an unknown-length plaintext. It did not evaluate the **length-committed**
design, in which the caller declares the plaintext length at construction. CCM
encodes that length in the first CBC-MAC block `B0` (RFC 3610 §2.2); once `B0`
is known the CBC-MAC and the CTR keystream both advance chunk by chunk with
`O(chunk)` memory and no buffering at all.

Two precedents, cited for exactly what each establishes and no more:

- **OpenSSL EVP SM4-CCM establishes the length-commitment contract.** A C
  caller must set the total plaintext length (an `EVP_EncryptUpdate` with a
  NULL output) before any payload. OpenSSL then still requires the payload in
  **one** call — it does not stream CCM
  ([openssl/openssl#25719](https://github.com/openssl/openssl/discussions/25719)).
  So OpenSSL is precedent for "declare the length first", not for the
  chunked encryptor. The `O(chunk)` encryptor is this crate's, and it follows
  from RFC 3610's structure (§2), not from any reference implementation.
- **The known-length profiles** the `mode_ccm` module documentation names —
  802.15.4 / Zigbee frames and TLS-CCM records — carry the length in a header
  before the payload arrives, which is what makes the commitment cheap for
  the callers this cycle is for.

So the feature that was a non-feature under one design is a genuine one under
the other: a real streaming *encryptor* with the memory story the v0.15
objection demanded, plus a decryptor that exists for API parity with
`Sm4GcmDecryptor` and is honestly labelled as what it is.

**What this cycle is not.** No new cryptography and no new dependency. The
encryptor is the single-shot `mode_ccm::encrypt` algorithm re-ordered around
chunk boundaries; the decryptor is a thin wrapper over the single-shot
`mode_ccm::decrypt` body. Both live behind the existing `sm4-aead` feature. The
default-features build stays byte-identical, and the C ABI is untouched
(Q12.10).

## 2. The structural fact the design rests on

`mode_ccm::encrypt` today:

1. `validate_params(nonce, pt_len, aad_len, tag_len)`;
2. `auth = B0 ‖ format(aad) ‖ plaintext ‖ zero-pad`, then `T = CBC-MAC(auth)`;
3. `S0 = E(A0)`; `tag = (S0 ⊕ T)[..tag_len]`;
4. `ct = plaintext ⊕ CTR(A1, A2, …)`.

Every quantity in steps 1–3 except the plaintext bytes themselves is known at
construction once `pt_len` is declared. The CBC-MAC is a chain — it absorbs
`B0 ‖ format(aad)` first and the plaintext blocks after, so the prefix can be
folded at construction and plaintext absorbed as it arrives. The CTR keystream
is indexed by block number, so it can be generated as needed with a leftover
buffer for partial-block chunks. Nothing about CCM prevents streaming
*encryption*; it only prevents streaming without a length commitment.

**The counter is CCM's, not GCM's.** `A_i` carries `i` as a **`q`-byte
big-endian** field in its trailing `q = 15 − nonce.len()` bytes, with
`A_i[0] = q − 1`. GCM's `inc32` increments the trailing **4** bytes. Even the
12-byte default nonce is `q = 3`, not a 32-bit counter — reusing
`gcm_streaming`'s counter advance would produce wrong ciphertext for every
nonce length. The streaming encryptor borrows GCM's leftover-keystream
*buffer* idiom only; the counter encoding comes from a helper extracted out of
`mode_ccm::ccm_ctr_xor` so it is never reimplemented by hand (Q12.5).

Decryption is different for the reason every AEAD decryptor is: releasing
plaintext before the tag verifies hands an attacker a chosen-ciphertext
distinguisher, so the output is buffered until `finalize_verify` regardless of
mode. CCM adds that the MAC runs over the *plaintext*, so no MAC work can begin
until the length is known — which for a stream is EOF. A decryptor therefore
buffers ciphertext and does all its work at finalize; that is the GCM
decryptor's memory shape (`O(message)`) with less spread-out compute, and it is
documented as such.

## 3. Forks for sign-off

### Q12.1 — Scope: encryptor and decryptor, not decryptor alone
**Settled 2026-09-01: both.** The encryptor is the component with the memory
story; the decryptor is API parity with the GCM pair and the natural consumer
of the encryptor's output. **Alternative (rejected):** decryptor only — the
smallest surface, but exactly the buffer-only shape Q15.11 called a
non-feature. **Alternative (rejected):** re-affirm the deferral — no consumer
has surfaced since v0.9, but the deferral rested on a design premise this cycle
overturns, and the surface is small.

### Q12.2 — Placement: a `ccm_streaming` sibling module under `sm4-aead`
**Recommend:** new file `crates/gmcrypto-core/src/sm4/ccm_streaming.rs`,
declared `#[cfg(feature = "sm4-aead")] pub mod ccm_streaming;` with a
module-comment block in `sm4/mod.rs` matching the `gcm_streaming` one, and
re-exported as `pub use ccm_streaming::{Sm4CcmDecryptor, Sm4CcmEncryptor};` —
the exact shape of `gcm_streaming` (`sm4/mod.rs:50` and `:90`). No new feature
flag: the types are meaningless without `mode_ccm`, and a new flag would pay
the seven-places tax (`Cargo.toml`, `deny.toml`, `ci.yml`, `api-stability.yml`,
clippy leg, MSRV leg, wasm32 leg) for nothing. Neither type derives `Debug`,
`Clone`, or `Copy` — `Sm4GcmEncryptor` / `Sm4GcmDecryptor` derive none, and a
`Debug` on a type holding round keys and plaintext is a leak vector.
**Alternative:** implement inside `mode_ccm.rs`. Keeps the helpers private but
takes the file past 1,100 lines and breaks the streaming-lives-beside-the-mode
precedent.

### Q12.3 — Encryptor API and the length-commit contract
**Recommend:**

```rust
pub struct Sm4CcmEncryptor { /* private */ }
impl Sm4CcmEncryptor {
    #[must_use]
    pub fn new(key: &[u8; KEY_SIZE], nonce: &[u8], aad: &[u8],
               plaintext_len: usize, tag_len: usize) -> Option<Self>;
    #[must_use]
    pub fn update(&mut self, chunk: &[u8]) -> Option<Vec<u8>>;
    #[must_use]
    pub fn finalize(self) -> Option<Vec<u8>>;
}
```

- `new` runs the same `validate_params` gate as the single-shot (nonce length
  in `[7, 13]`, `tag_len` in `{4, 6, 8, 10, 12, 14, 16}`, `plaintext_len`
  representable in `q = 15 − nonce.len()` bytes) and returns `None` on any
  failure. Unlike `Sm4GcmEncryptor::new`, this constructor is fallible —
  CCM has parameters GCM does not. **AAD is construction-only**, as for the
  GCM pair: `new` formats it (`B0 ‖ format(aad)`), folds it into the CBC-MAC,
  and drops the formatted buffer. The constructor therefore allocates
  `O(aad)`; the `O(chunk)` claim is for the streaming phase and the docs say so.
- `update` returns the ciphertext for `chunk` (same length; CCM neither pads
  nor buffers output). The bound check is `fed.checked_add(chunk.len())` on
  `u64` (the `Sm4GcmEncryptor::update` rule — wasm32 is a first-class target
  and a wrapping `usize` add would miss the bound and then overrun the
  `q`-byte counter); a `None` from the checked add is treated as an
  over-feed. **An overflowing `update` emits nothing** — the whole chunk is
  rejected before any XOR, exactly as GCM's ceiling check rejects before
  encrypting — and the encryptor is **poisoned**: every later call returns
  `None`. Already-emitted ciphertext is not retracted (it cannot be) but no
  tag will ever authenticate it. `update(&[])` is a no-op returning
  `Some(vec![])` when it does not exceed the bound.
- `finalize` returns the `tag_len`-byte tag, or `None` if the encryptor is
  poisoned **or under-fed** (`fed != plaintext_len`). A partial stream is never
  tag-authenticated: the length in `B0` is a commitment, and an under-fed
  finalize would produce a tag over a message the caller did not send.
  **This is an intentional divergence from `Sm4GcmEncryptor::finalize`**,
  which still returns a tag after poison (its docs merely say not to call
  it). CCM's `Option` here is the stricter contract, chosen on purpose, not a
  by-product of the variable tag length.
- The tag is returned separately, not appended, matching `Sm4GcmEncryptor` and
  the wire layout the decryptor consumes (Q12.4). Callers wanting the
  single-shot's `ct ‖ tag` concatenate.
- **CTR generation within a chunk:** whole blocks are batched through
  `Sm4Cipher::encrypt_blocks` (the single-shot's path, so bulk chunks keep
  the SIMD fanout under `sm4-bitsliced-simd`); the trailing partial block, if
  any, is one `encrypt_block` whose unused keystream bytes become the
  leftover for the next call. Byte-identical either way; documented so a
  reviewer does not "simplify" it to per-block and quietly lose the fanout,
  or the reverse.

**Alternative:** `finalize` returning `Vec<u8>` unconditionally with the
under-feed case producing a tag over the shorter message. Rejected: it turns a
caller bug into a validly-tagged message with the wrong declared length and
recreates the class of truncation confusion CCM's `B0` exists to prevent.

### Q12.4 — Decryptor API: length-free, commit-on-verify, thin, latched
**Recommend:**

```rust
pub struct Sm4CcmDecryptor { /* private */ }
impl Sm4CcmDecryptor {
    #[must_use]
    pub fn new(key: &[u8; KEY_SIZE], nonce: &[u8], aad: &[u8]) -> Option<Self>;
    pub fn update(&mut self, chunk: &[u8]);
    #[must_use]
    pub fn finalize_verify(self, tag: &[u8]) -> Option<Vec<u8>>;
}
```

- No length parameter: a decryptor frequently does not know the payload length
  until EOF, and requiring it would make the type strictly harder to use than
  the GCM decryptor for no memory gain (the output must be buffered until
  verification either way).
- `new` validates the nonce length early (`None` outside `[7, 13]`) so a
  misconfigured decryptor fails before it buffers a message, and computes the
  `q`-derived payload ceiling `2^(8q) − 1` (for `q ≥ 8`, unbounded). It
  stores the `Sm4Cipher` (round keys — a secret; see Q12.6), the nonce
  (inline `[u8; 13]` plus length), and an **owned copy of the AAD**, which
  the CBC-MAC cannot consume until the length is known at finalize. The AAD
  is a header; `O(aad)` retention is documented.
- `update` appends to an internal ciphertext buffer and emits nothing. **It
  latches an overflow flag** when `buffer.len().checked_add(chunk.len())`
  would exceed the `q`-derived ceiling (or the checked add fails), and stops
  buffering from that point. The GCM decryptor latches at `2^36 − 32` for the
  same reason, and for CCM the ceiling is small enough to matter: a 13-byte
  nonce — the 802.15.4 / TLS-CCM profile §1 cites — caps the payload at
  65 535 bytes, so without the latch a misbehaving peer could make the
  decryptor buffer gigabytes that `finalize_verify` would then reject.
- `tag_len` is not known until `finalize_verify` and is taken from
  `tag.len()`, exactly as `Sm4GcmDecryptor::finalize_verify` does; an invalid
  length is `None`.
- `finalize_verify` returns `None` if the overflow flag is set, else runs the
  single-shot body `decrypt_with_cipher(&cipher, nonce, &aad, &buffer, tag)`
  (Q12.5 — split `(ct, tag)` arguments, so no `buffer ‖ tag` copy) and returns
  the plaintext only on tag verification. On failure the tentative plaintext
  is zeroized by that body — it is today's code.

**Why thin matters (the assurance premise, as in v1.11 Q11.8):** because the
decryptor adds no cryptography over `mode_ccm::decrypt`, it rides the existing
`ct_sm4_ccm_decrypt` dudect target (Q12.8), and that thinness is guarded by
the differential fuzz target (Q12.9) rather than by this paragraph.

**Alternative:** a length-declared decryptor mirroring the encryptor, doing
CTR + CBC-MAC per chunk and buffering plaintext. Spreads compute, but keeps an
unverified plaintext buffer alive across calls (a larger zeroize surface),
forces the caller to know the length before EOF, and would be new
secret-touching code needing its own dudect target — and would **void Q12.8**.
Rejected.

### Q12.5 — `mode_ccm` refactor: promote helpers, extract the counter encoder, split `decrypt`
**Recommend**, all at **`pub(super)`** (the `mode_gcm` precedent: `inc32`,
`gctr`, `derive_j0` are `pub(super)` for `gcm_streaming`; only the
`GCM_MAX_PT_BYTES` constant is `pub(crate)`):

- Promote `validate_params`, `build_b0`, `format_aad_into` from private to
  `pub(super)`.
- **Extract the `A_i` encoder** from the body of `ccm_ctr_xor` into
  `pub(super) fn counter_block(a0: &[u8; BLOCK_SIZE], i: u64) -> [u8; BLOCK_SIZE]`
  (writes `i` as the `q`-byte big-endian trailing field, `q` read from
  `a0[0] + 1`), and make `ccm_ctr_xor` call it. One encoder, used by both the
  single-shot and the streaming path — the `q`-byte-vs-`inc32` trap (§2) is
  then structurally impossible to fall into. A code comment at the encoder
  states the width argument: `fed_len ≤ plaintext_len ≤ 2^(8q) − 1` is
  enforced at `new`, so the block index never exceeds the field.
- Factor the body of `decrypt` into
  `pub(super) fn decrypt_with_cipher(cipher: &Sm4Cipher, nonce: &[u8], aad: &[u8], ct: &[u8], tag: &[u8]) -> Option<Vec<u8>>`
  taking the ciphertext and tag **already split** (the public `decrypt`
  already splits `ciphertext_with_tag`; the decryptor already holds them
  apart). The public `decrypt` becomes: validate `tag_len`, split, `Sm4Cipher::new(key)`,
  delegate.

The public single-shot API, its outputs, and its KATs do not change; the
existing `fuzz_sm4_ccm_decrypt` / `fuzz_sm4_ccm_encrypt` sweeps gate the
refactor. No item becomes `pub` — nothing new enters the SemVer surface from
this refactor.
**Alternative:** duplicate the helpers in `ccm_streaming.rs`. Rejected: two
copies of `B0` formatting or of the counter encoding is exactly the drift the
differential tests would then be needed to catch.

### Q12.6 — Zeroize
**Recommend:** `Sm4CcmEncryptor` derives `Zeroize` + `ZeroizeOnDrop`. Its state
carries plaintext-derived bytes across calls — the CBC-MAC partial block (raw
plaintext), the running `T`, and the leftover keystream — and `Sm4Cipher`
already zeroizes on drop, so this is the crate's established best-effort
posture applied consistently.

`Sm4CcmDecryptor` **does hold a secret** — the `Sm4Cipher` round keys — and
relies on that field's existing `ZeroizeOnDrop` via normal field drop; it
derives nothing itself because its other state is public (ciphertext buffer,
AAD, nonce) and no plaintext exists until `finalize_verify` succeeds (the
failure path inside `decrypt_with_cipher` zeroizes the tentative plaintext
already). The docs say "holds the key schedule; zeroized on drop" rather than
"holds no secrets". The usual caveat applies and is restated in the module
docs: stack copies and register spills are outside what `zeroize` can reach.
**Note for review:** `Sm4GcmEncryptor` does **not** currently zeroize its
leftover keystream, and `GhashAcc` holds `H` and the running `y`. Bringing the
GCM pair into line is a real follow-up (not a one-liner) outside this cycle's
diff; it is recorded in §6, not folded in.

### Q12.7 — Failure modes
Every fallible operation returns `Option`; `None` covers, without distinction:
invalid nonce length; invalid tag length; `plaintext_len` too large for `q`;
over-feed or checked-add failure (encryptor, with poison); under-feed at
`finalize`; buffered ciphertext past the `q` ceiling (decryptor, latched); tag
mismatch. This is the workspace failure-mode invariant (`SECURITY.md`); a PR
that adds a distinguishing variant is rejected on that basis.

### Q12.8 — Dudect: no new target (count stays 20)
**Recommend: none**, with the rationale recorded in `SECURITY.md` beside the
v1.11 paragraph:

- The **encryptor's** secret-dependent work is the same `Sm4Cipher::encrypt_block(s)`
  chain the single-shot runs (CBC-MAC over plaintext, CTR keystream). Its
  only new control flow — chunk boundaries, the leftover position, the
  declared length, and the over-/under-feed arms — is over **public**
  quantities. Encryption has no tag comparison and **no secret-dependent
  failure arm** (its failure arms are public-length checks, as
  `Sm4GcmEncryptor`'s are). `Sm4GcmEncryptor` has no target on the same
  reasoning, and `ct_sm4_ctr_encrypt` already gates the keystream path
  class-split by key.
- The **decryptor** is a thin wrapper over the single-shot body already
  measured by `ct_sm4_ccm_decrypt`; the code that touches the key is
  byte-identical, and the differential fuzz target fails the sweep if a future
  rewrite quietly reimplements mode logic in the wrapper.

**Void condition, stated so it cannot be forgotten:** this "no new target"
holds **only while the decryptor stays a delegator**. A length-declared
decryptor, an incremental CBC-MAC over unverified plaintext, or CTR-before-
finalize inside the decryptor introduces a new secret-touching body and
reopens the dudect question — which is one reason the Q12.4 alternative is
rejected rather than merely deferred.

**Alternative:** a `ct_sm4_ccm_decrypt_buffered` target mirroring
`ct_sm4_gcm_decrypt_buffered`. Rejected: that GCM target exists because the GCM
decryptor carries a genuinely new secret-touching body (the running GHASH
accumulator). The CCM decryptor carries none; a target would measure the same
window twice and add a slot to a matrix whose noise budget (see
`docs/v0.5-dudect-recalibration.md`, 2026-09-01) is already the cycle's most
expensive resource.

### Q12.9 — Fuzz: two differential targets (census 33 → 35)
**Recommend**, with layouts pinned because the GCM templates cannot be copied
verbatim:

- **`fuzz_sm4_ccm_streaming_decrypt`** — front-consuming layout
  `[key:16][tl:1][tag:tl'][nl:1][nonce:nl'][al:1][aad:al'][chunk:1][ct:rest]`,
  where `tl' = tl % 18` (so both the seven valid tag lengths *and* invalid
  ones occur), `nl' = nl % 17`, `al' = al % 33`. Oracle:
  `mode_ccm::decrypt(&key, &nonce, &aad, &(ct ‖ tag), tag.len())` — the
  single-shot takes `ciphertext ‖ tag` plus `tag_len`, **not** GCM's split
  `(ct, tag)`, and this is the line most likely to be wired wrong. Streaming
  side: `Sm4CcmDecryptor::new` (a `None` here is the streaming side's `None`
  and must coincide with the oracle's), feed `ct` in chunks of
  `max(1, chunk)`, `finalize_verify(&tag)`. Assert equality of the two
  `Option<Vec<u8>>`s.
- **`fuzz_sm4_ccm_streaming_encrypt`** — layout
  `[key:16][tl:1][nl:1][nonce:nl'][al:1][aad:al'][chunk:1][mode:1][pt:rest]`,
  where **`mode % 3` selects the declared length independently of the bytes
  fed**: `0` → `plaintext_len = pt.len()` (exact; assert streaming
  `ct ‖ tag` byte-equals `mode_ccm::encrypt` whenever the single-shot accepts
  the parameters, and that `mode_ccm::decrypt` round-trips it); `1` →
  `plaintext_len = pt.len() + 1 + (chunk as usize)` (under-feed; assert
  every `update` succeeds and `finalize` is `None`); `2` →
  `plaintext_len = pt.len().saturating_sub(1 + chunk as usize)` with
  `pt` non-empty (over-feed; assert the first overflowing `update` is `None`,
  emits nothing, and every later call is `None`). The `fuzz_sm4_gcm_encrypt`
  template sets fed length = remaining bytes, so its over-/under-feed arms
  can never fire; this layout exists to make them fire.

Both take SM4, so both go in `FUZZ_TARGETS` **and** `FUZZ_SIMD_TARGETS`; each
gets a committed `fuzz/seeds/<target>/` directory (the #117 preflight fails
the nightly otherwise). Seed layouts follow the `arbitrary` 1.4.2
front-consuming order pinned by `fuzz/Cargo.lock`.

### Q12.10 — FFI: deferred to a follow-up cycle
**Settled 2026-09-01: defer.** The v0.9 → v0.10 precedent — Rust streaming
semantics ship first, the permanent C ABI follows once they have settled.
The `gmcrypto_sm4_ccm_encryptor_*` / `_decryptor_*` handle family (lifecycle
identical to the GCM streaming handles) is recorded as the **v1.13 candidate**.
No `aead-traits` change either: `aead` 0.6 has no `aead::stream`, so the
streaming types stay inherent-only exactly as the GCM pair does.

### Q12.11 — Terminology
**Recommend:** the module and type docs use two fixed phrases and never the
bare word "streaming" for the decryptor: the encryptor is
**"length-committed streaming"**; the decryptor is **"incremental-input
buffered"** (the GCM term). The v0.15 objection (Q15.11) is cited in the module
docstring and answered there, so a future reader sees why the name changed
rather than assuming the objection was forgotten.

## 4. Assurance plan

| Layer | What proves it |
|---|---|
| Unit — encryptor | Chunked-equals-single-shot over chunk sizes `{1, 7, 15, 16, 17, 31, 32, 33, 100, whole}` for a 200-byte payload; all seven tag lengths; all nonce lengths 7–13; empty AAD; `plaintext_len = 0`; `update(&[])` is a no-op (the `encryptor_empty_updates_are_noops` GCM precedent); over-feed emits nothing, poisons, and stays poisoned; `finalize` after poison → `None`; under-feed `finalize` → `None`; `new` rejects each invalid parameter |
| Unit — decryptor | Same chunk matrix against `mode_ccm::decrypt`; tag mismatch → `None`; invalid `tag.len()` → `None`; invalid nonce → `new` is `None`; **13-byte nonce fed 65 536 bytes latches in `update` and `finalize_verify` is `None`**; empty updates then verify; round-trip from the streaming encryptor |
| KAT | The existing OpenSSL-sourced CCM vectors (`docs/v0.8-ccm-kat-sourcing.md`) driven through both streaming types in ≥2 chunkings |
| Single-shot regression | Existing `mode_ccm` tests and KATs unchanged after the Q12.5 refactor; `counter_block` unit-tested against the pre-refactor inline encoding for `q ∈ 2..=8` |

## 5. Risks

- **The Q12.5 refactor perturbing the single-shot.** Mitigation: the public
  `decrypt` becomes a validate-split-delegate; `ccm_ctr_xor` calls the
  extracted encoder; the existing KATs and `fuzz_sm4_ccm_decrypt` /
  `fuzz_sm4_ccm_encrypt` sweeps are unchanged and gate it.
- **Counter encoding.** The `q`-byte-vs-`inc32` trap (§2) is closed
  structurally by the shared `counter_block` helper; the residual risk is the
  width argument, which is pinned in a comment at the encoder and covered by
  the all-nonce-lengths unit matrix.
- **Partial-block bookkeeping bugs** in the CBC-MAC accumulator or CTR
  leftover. Mitigation: chunk size 1 and every block-boundary neighbour are in
  the unit matrix; the fuzz targets draw chunk sizes freely.
- **Integer overflow on 32-bit targets.** Closed by `checked_add` on `u64` in
  both `update`s (Q12.3, Q12.4).
- **Nonce reuse across encryptor instances** is the caller's contract, as for
  every mode here; restated in the type docs with the CCM-specific note that a
  `(key, nonce)` pair also fixes `B0`, so two encryptors with the same pair and
  different `plaintext_len` are still a nonce reuse.
- **`O(message)` decryptor memory** could surprise a caller who read
  "streaming" on the encryptor. Mitigation: Q12.11 — the decryptor is never
  called streaming — and the Q12.4 latch bounds it by the nonce's ceiling.

## 6. Out of scope

FFI projection (v1.13 candidate, Q12.10); `aead-traits` integration (no
`aead::stream`); a length-declared decryptor (Q12.4 alternative — voids
Q12.8); bringing `Sm4GcmEncryptor` / `GhashAcc` under zeroize (Q12.6 note);
any change to `mode_ccm`'s **public single-shot API or outputs** (the
`pub(super)` refactor and the module-doc correction in Q12.12 are in scope);
AVX-512 `sbox_x64` and F21, which stay on the deferred list as before.
