# v1.11.1 release review checklist (three-crate workspace)

The reviewer runbook for the **1.11.1** publish. Adapted from
`docs/v1.9.1-release-review.md` (the last patch-shaped runbook) and
`docs/v1.11.0-release-review.md` (the current command set). 1.9.1's headline
check was "is the licence text actually in the archive?"; 1.11.0's was "is it
genuinely additive?". **1.11.1 is a patch for two defects** (the second
exposed by the first — see "The re-cut" below), so its headline check is
threefold: *is the default build genuinely wire-identical to 1.11.0*, *is the
opt-in SIMD path genuinely fixed, on both architectures*, and *is the `tlcp`
deprotect genuinely length-independent on the hardware that showed it was
not?*

**Publish order is `gmcrypto-simd` → `gmcrypto-core` → `gmcrypto-c`.** The
intra-workspace path-deps are pinned exactly (`=1.11.1`), so each crate must be
live on crates.io before the next resolves. `gmcrypto-simd` is where the repair
(`sbox_x4`) lives, so it is not optional in this patch even though its public
API is unchanged.

**`cargo publish` and the SSH-signed tag are the maintainer's authenticated call,
never the agent's.** The 1.11.0 publish was a recorded one-off delegation, not a
standing grant (CLAUDE.md, "Release state").

**What this release is.** On 1.11.0, enabling the opt-in `sm4-bitsliced-simd`
feature makes *serial* SM4 — the CCM CBC-MAC path, and any single-block use —
**slower than the scalar build**: `tau` called a one-byte-to-x8 adapter four
times per word, so AArch64 paid 32 scalar S-box evaluations where four are
required (#163). #165 replaced that with a four-byte `sbox_x4` entry (one NEON
x16 on AArch64; four scalar circuit calls on x86_64). Batch paths
(`sbox_x16`/`sbox_x32`) are unchanged. #166 made the repaired composition a CI
fact on both architectures and added a SIMD fuzz profile. Everything else on
`main` since `v1.11.0` is assurance, CI, records, and C example-file work —
**until the first cut of this patch (`8cb4aac`) was held.**

**The re-cut (second fix).** The first cut's dudect evidence failed
`ct_tlcp_cbc_deprotect` on Zen 4 / Xeon 8573C runners (the "dudect note" and
its correction at the end of this file). Root cause: since v1.7 the TLCP
SM4-CBC deprotect equalized the inner-HMAC SM3 compression *count* but
computed the MAC through the streaming hasher, whose buffer copy and
finalize-padding branch stayed secret-length-dependent; fix 1 made that
residual measurable. #169 rewrote the inner HMAC as a fixed-schedule,
constant-time construction (`tlcp::record::mac_ct`). Same block count, no
extra SM3 work, MAC values and wire bytes unchanged. 9V74 PR smoke: 0.32–0.42
→ **0.026**. So this patch now carries **two** source changes: the
`sm4-bitsliced-simd` path (opt-in) and the `tlcp` deprotect path (every
`tlcp` user; default build wire-identical, timing behaviour deliberately
changed).

**Audience, stated precisely.** (1) The serial-SM4 repair executes only when
`sm4-bitsliced-simd` is selected. `sm4-aead` (and so `gmcrypto-c`, and the
envelope's `aead` feature) pulls `gmcrypto-simd` and *compiles* its
unconditional `sbox_x4` module, but never selects the repaired serial path —
compiled, not executed. (2) The `tlcp` fix executes in every build that
enables `tlcp`: that includes **`gmcrypto-c`** (its core features list
`tlcp`) and every C-ABI consumer of `gmcrypto_tlcp_*` CBC deprotect. Default
`gmcrypto-core` is `default = []`, enables neither, and is therefore
behaviour- *and* timing-identical to 1.11.0; "wire-identical" in the
CHANGELOG is the claim for `tlcp`-enabled builds, whose timing deliberately
changes.
This patch deliberately changes no downstream or C-ABI feature default — that
is a separate product/security-posture decision (SIMD backends carry no
constant-time claim), recorded as a named follow-up.

Use `BLOCK` (do not publish until fixed/deferred), `WARN` (publishable, track),
`INFO` (note only).

**(c) The defect is actually gone — serial SM4 under SIMD is no faster-than-
scalar claim, but it must no longer be *slower*.**

The CHANGELOG `[1.11.1]` carries the measured table (Apple M1 Pro, release,
5-sample median): CCM encrypt `sm4-aead` 0.24 MiB/s → `sm4-aead,sm4-bitsliced`
0.39 → `sm4-aead,sm4-bitsliced-simd` **1.63** (on 1.11.0 the SIMD figure was
*below* scalar). Reproduce if you have the machine; the bench harness is the
one described in the #165 PR. **x86_64 throughput is unmeasured and this
release makes no throughput claim for it.** 1.11.0's serial path on an AVX2
host was four AVX2 x8-circuit invocations; 1.11.1's is four scalar circuit
calls. Relative wall time between those is microarchitecture-dependent and
has not been measured on any x86 host — "four scalar calls cannot be slower"
is not a structural guarantee and is not claimed. What x86_64 has is
correctness coverage: the core test suites under both SIMD feature sets, the
million-round KAT, and the SIMD fuzz profile (§3b), all on x86_64 CI runners.
Every "no longer slower" statement in README / CHANGELOG is scoped to the
measured AArch64 path. The AVX2-host decision matrix (#165's open item: Intel
and AMD, x8-AVX2 vs four-scalar, ≥30 paired trials) is a named follow-up,
not a precondition of this patch.

**What this patch did and did not change.** `tlcp::record::deprotect_cbc`
and `mac_equalized` are byte-identical to 1.11.0 (§0); whatever residual
the target sees on Zen 4 is in the published 1.11.0 too. The one way this
patch could *amplify* the reading is dilution: slot 4 enables
`sm4-bitsliced-simd`, #165 makes the serial SM4-CBC decrypt inside the
window ~8× cheaper on x86, and a fixed residual becomes a larger share of a
smaller window. Tested directly on Apple M1 at the 10K budget, 3 runs each:
`tlcp` alone 0.049 / 0.085 / 0.091; `tlcp,sm4-bitsliced-simd` 0.045 /
0.039 / 0.049 — **SIMD does not raise it on AArch64**, and the residual is
not visible there at all.

**On x86 it does.** A nightly (100K×5) dispatched on the merged release
commit `8cb4aac` (run 32557364267) drew an Intel Xeon 8573C for slot 4 and
read **0.3011** with all five runs in 0.29–0.32 — a tight cluster, failing
the gate at the full nightly budget. The only other nightly this repository
has run on an 8573C, 2026-08-11 on pre-#165 `e7e85e7`, read **0.1229**
(runs 0.11–0.16). Same hardware class, same budget, same target code,
before and after the SM4 repair: 0.12 → 0.30. The 7763 nightlies tell the
same story more quietly — pre-#165 0.053–0.077, post-#165 0.0989. In every
one of these runs every SIMD-specific target reads ≤ 0.01 and
`negative_control` fires, so the harness is not the thing that moved.

The mechanism is the dilution described above. It is *not* a new
secret-dependent branch: the absolute class-to-class timing difference in
`deprotect_cbc` is whatever it was in 1.11.0, and `sbox_x4` is a
data-independent gate circuit. What changed is that the SIMD configuration
now spends ~8× less time in SM4 around that residual, so both the mean and
the jitter of the window shrink and the residual's effect size — which is
what `|tau|` measures — grows. A real adversary benefits from the same
noise reduction, so "unchanged in absolute terms" is true but not a full
defence: the same signal, less noise, is a somewhat more exploitable
signal. That is inherent to any speed-up that sits inside an imperfectly
equalised window.

**What it means.** `ct_tlcp_cbc_deprotect` class-splits on the recovered
fragment length with a fixed key; the equalization tops up the SM3
compression *count*, but the two classes still do different partial-block
buffering / finalize-padding work inside `HmacSm3` and different-length MAC
extraction. On Zen 3 that residual sits under the gate; on Zen 4 it does
not, reliably, at 10K. That is a finding about the Lucky13 equalization on
one microarchitecture, present since v1.7, and it belongs to an assurance
cycle (a `tlcp`-only x86 measurement to settle the dilution question, then
instrumenting the three surfaces on a Zen 4 host) — not to this patch.

**Effect on this release — BLOCK, pending the maintainer's decision.** As
written, §8 ("gated targets stay under 0.20") is **not met at the nightly
budget** on the release commit, in the one configuration (`sm4-bitsliced-simd`
+ `tlcp`, x86) that 1.11.1's own audience runs. 1.11.1 would be the first
release shipped with its own nightly constant-time gate red. The agent did
not publish and does not recommend publishing this commit as-is.

Honest arguments on each side, for the decision:

- *Ship anyway.* The residual is in the published 1.11.0 (masked at ~0.12
  by slower SM4); holding 1.11.1 protects no one from it while leaving SIMD
  callers on the CCM regression; `SECURITY.md` already says SIMD backends
  carry no constant-time claim; `gmcrypto-c` and every `sm4-aead`-only
  downstream never compile this configuration.
- *Hold.* The project's standard is its gate, and the gate fails
  reproducibly (five runs within 0.03 of each other). Shipping a speed-up
  that makes a Lucky13 residual more measurable, under a flag that exists
  to be turned on in production, contradicts the posture `SECURITY.md`
  sells. The fix is plausibly small and local: make `mac_equalized` /
  `deprotect_cbc` length-independent in the parts the compression-count
  top-up does not cover (the `HmacSm3` partial-block buffering and
  finalize-padding path, the MAC extraction), verified by the same target
  reading ≤ 0.20 on an 8573C / 9V74 at 100K. That is a `tlcp` core change
  and would ride in this same patch line (1.11.1 re-cut, or 1.11.2).

Recommended: **hold**; open the `tlcp` equalization finding as a tracked
issue with this table; fix it on a branch; re-run the nightly on the fix
until a 9V74 or 8573C is drawn (the runner cannot be chosen — record the
CPU model of every run); then re-cut the patch with both fixes and a
re-run Gate #1. Feed the hardware heterogeneity into the next dudect
re-baseline (`docs/v0.5-dudect-recalibration.md`) rather than re-running
until a 7763 is drawn. No gate or threshold was changed here.

### Resolution (2026-08-22) — held, fixed, re-cut

The maintainer chose **hold and fix**. #169 replaced `mac_equalized` with
`mac_ct` (`tlcp/record.rs`): the inner HMAC-SM3 is computed over a fixed,
public block schedule — `1 + ⌈(13 + max + 9)/64⌉`, identical to what the
dummy compressions already paid — with every byte chosen by `subtle`
selection among message / `0x80` / zero / length field on the public
candidate region, and the digest state selected at the secret final-block
index by `u32` masks. All control flow is on public quantities; the secret
length enters only through `ct_lt` / `ct_eq` / `conditional_select` and a
shift. The outer hash is fixed-length. MAC values and wire bytes are
unchanged; two `pub(crate)` tests pin equivalence with `HmacSm3` for every
length under every bound and the public-only schedule.
