# v1.11.1 — ECOSYSTEM §8 Gate #1 evidence

current tip, in every feature configuration the crate ships, executed by its
scripted gate — to pass against every `gmcrypto-core` release candidate before
it ships. This file is that record for the **1.11.1** candidate.

`--features aead`), 0 failures. No runtime or API incompatibility, so **no
migration note is required** before this release ships.

the old 0.1.0-RC-suite rule), this run used the scripted gate that §8 now
names, so the table below is the script's own output rather than transcribed
command output. The script fails closed: a recorded run is a passing run.

## 3. Verdict

`gmcrypto-core` 1.11.1 is compatible with `gmcrypto-envelope-lite` 0.4.0
(`0c7f983`) in every configuration the envelope ships. The candidate's only
non-comment source change since `v1.11.0` sits on the
`#[cfg(feature = "sm4-bitsliced-simd")]` path (see
`docs/v1.11.1-release-review.md` §0), and no envelope configuration enables
that feature — so the envelope compiles code that is behaviour-identical to
1.11.0 in both phases.

## 4. What this gate does and does not establish

It establishes **compatibility**: the envelope builds and its entire suite
passes against the candidate, with and without `aead`.

It does **not** establish that any downstream **consumes the repair**. The
envelope's `aead` feature is `["gmcrypto-core/sm4-aead"]` only; it never
selects `sm4-bitsliced-simd`, so the repaired `tau` → `sbox_x4` composition
is not on any code path this gate compiles. The same is true of `gmcrypto-c`
(`sm4-aead` always-on, no SIMD feature). That is by design for this patch —
its audience is Rust callers who *already* opted into `sm4-bitsliced-simd`
on 1.11.0 — and it is why the patch carries no envelope or C-ABI feature
change. Whether a downstream should enable SIMD is a separate decision with
its own security-posture narrative (SIMD backends carry no constant-time
claim), recorded as a named follow-up, not a precondition of this release.

The evidence that the repaired path itself is correct lives elsewhere:
`docs/v1.11.1-release-review.md` §3 (CI on both architectures, the
million-round KAT under the feature, the SIMD fuzz profile — all landed in
#166). §5 below closes the consumption gap for this candidate specifically.

### 5.2 Throughput probe, from the envelope's side

A throwaway `examples/throughput_probe.rs` in the disposable copy — not
committed anywhere — seals a 1 MiB payload through the real `SecureClient`
(SM2 wrap + sign included), opens it, then opens a forged copy (one cipher
byte changed; must fail). Apple M1, release, 5-sample median, MiB/s. The
forged-CCM open is the #163 symptom: CBC-MAC over the whole body is serial
SM4 end to end.

| core | envelope features | GCM seal | GCM open | CCM seal | CCM open | CCM forged-open |
|---|---|---|---|---|---|---|
| crates.io 1.11.0 | `aead` | 0.58 | 0.58 | 0.30 | 0.30 | 0.29 |
| crates.io 1.11.0 | `aead` + `sm4-bitsliced-simd` | 8.45 | 8.42 | **0.14** | **0.14** | **0.14** |
| candidate 1.11.1 | `aead` | 0.58 | 0.58 | 0.29 | 0.29 | 0.29 |
| candidate 1.11.1 | `aead` + `sm4-bitsliced-simd` | 8.52 | 8.45 | **2.09** | **2.07** | **2.10** |

Read across the rows:

- **Rows 1 vs 3 — the patch is a no-op for the envelope as shipped.** With
  `aead` only, every number is unchanged to the second decimal. This is the
  "default build behaviour-identical" claim, measured rather than argued, on
  the one downstream that exists.
- **Row 2 — the published defect, reproduced from the consumer.** On 1.11.0,
  opting into SIMD *halves* CCM throughput (0.30 → 0.14) while GCM bulk
  gains 14×. A consumer who enabled the feature for GCM paid for it on CCM.
- **Row 4 — the patch fixes it.** Same feature, candidate core: CCM 0.14 →
  2.09 (15×), GCM unchanged. SIMD is now never slower than scalar for
  either mode, which is the whole claim of 1.11.1.

GCM forged-open is ~52 MiB/s in every row: GHASH rejects before any SM4
runs, so it never touched the serial path and is unaffected by either the
defect or the fix.

### 5.3 What this changes about the verdict

§3's PASS stands; §4's caveat is now closed for this candidate by direct
measurement: the envelope has run its whole suite over the repaired
composition and observed the repair. It does **not** change the envelope's
shipped feature set — `aead` remains `sm4-aead` only, by the decision
recorded in the #163 plan — and it does not make `sm4-bitsliced-simd` part
of the gate. Both are separate, named follow-ups.

One downstream obligation surfaced by 5.1, for the envelope repository after
1.11.1 is live: when it bumps its lock to 1.11.1, the
`cryptographic_dependency_inventory_records_the_reviewed_root_lockfile`
assertion and `docs/security/cryptographic-dependencies.md` must be updated
together with the new registry checksum — the test exists precisely so that
bump cannot happen silently.
