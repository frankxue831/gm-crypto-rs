# v1.9.1 release review checklist (three-crate workspace)

**Crates:** `gmcrypto-simd` 1.9.1 → `gmcrypto-core` 1.9.1 → `gmcrypto-c` 1.9.1
(published in that order; a crate must be live on crates.io before its dependents).
**Repository:** <https://github.com/frankxue831/gm-crypto-rs>
**Release candidate:** record the exact commit you intend to tag with
`git rev-parse HEAD` (the merge commit of the `release/v1.9.1` PR on `main`).
Review a frozen commit, not "latest main".
**Purpose:** decide whether that exact commit is safe to publish.

**What this release is.** A patch with **zero runtime behavior change**. The only
`src/` delta since 1.9.0 is inline `// SAFETY:` comments in the C shim (#115);
`crates/gmcrypto-core/src` and `crates/gmcrypto-simd/src` are **byte-identical to
the `v1.9.0` tag**. It exists to carry a genuine packaging defect fix to
crates.io: every `.crate` archive through 1.9.0 shipped **no licence text at
all**. Published versions are immutable, so this is fixable only going forward.

Publishing to crates.io is permanent. A yanked version is hidden from normal
resolution, but the `.crate` archive remains downloadable.

Use `BLOCK` (do not publish until fixed/deferred), `WARN` (publishable, track for
1.9.2/1.10), `INFO` (note only).

## 0. Provenance — this really is behavior-free

| Check | Command | Expected |
|---|---|---|
| 0.1 | `git diff --stat v1.9.0..HEAD -- crates/gmcrypto-core/src crates/gmcrypto-simd/src` | **empty** — the two baselined crates' sources are byte-identical to 1.9.0 |
| 0.2 | `git diff v1.9.0..HEAD -- crates/gmcrypto-c/src` | comments only (`// SAFETY:` blocks); no statement/expression change |
| 0.3 | `CHANGELOG.md` `[1.9.1]` | present, dated, and states "No API / ABI / wire change" |

If 0.1 is non-empty, this is **not** a patch — stop and re-scope.

## 2. Exact sibling pins (the lockstep contract)

```bash
grep -n 'gmcrypto-simd' crates/gmcrypto-core/Cargo.toml   # version = "=1.9.1"
grep -n 'gmcrypto-core' crates/gmcrypto-c/Cargo.toml      # version = "=1.9.1"
```

Expected: both read `version = "=1.9.1"` (not `"1.9"`/`"^1.9"`). A non-exact req
would let a dependent resolve against a mismatched sibling 1.x.

## 3. THE HEADLINE CHECK — licence text is actually in the archives

This is the entire reason 1.9.1 exists. If it fails, **do not publish**.

```bash
for c in gmcrypto-simd gmcrypto-core gmcrypto-c; do
  echo "== $c =="
  cargo package --list -p "$c" | grep -i license
done
```

Expected: **both** `LICENSE-APACHE` and `LICENSE-MIT` listed for **each** of the
three crates. An empty result for any crate means the defect is unfixed and the
release is pointless.

Also confirm `license = "MIT OR Apache-2.0"` (the dual widening) resolves for all
three, and that each crate directory holds its own copies:

```bash
ls crates/*/LICENSE-APACHE crates/*/LICENSE-MIT
```

## 9. ECOSYSTEM §8 Gate #1 — the downstream compatibility gate

`docs/ECOSYSTEM.md` §8 makes the `gmcrypto-envelope-lite` 0.1.0 RC suite a gate on
**every** `gmcrypto-core` release. Run both phases in a **temporary export**, never
in the real downstream checkout:

- **Phase 1 (pristine):** the six §8 commands against the committed lockfile,
  including the strict `release_documents` target and the cryptographic inventory
  against the registry lock.
- **Phase 2 (patched):** inject the 1.9.1 candidate via `[patch]` or a temporary
  path dep; run **without** `--locked` so cargo may rewrite only the disposable
  lockfile. `release_documents` is the sole deliberate post-patch exclusion.
  The downstream exact pin `=1.9.0` no longer resolves — bump it **only in the
  temporary gate copy**.

Record both phases' output and the exact tested core + envelope commit SHAs as
release evidence. A breaking result requires a documented migration note before
this release ships.

Known tolerated divergence: `gmcrypto-envelope-lite` is still Apache-2.0-only
against the charter's dual-licence rule, "until its own next release."

## 11. Publish dry-runs + package contents (in publish order)

```bash
cargo publish -p gmcrypto-simd --dry-run     # the only one that can fully dry-run
cargo package -p gmcrypto-core --list | sort # content review (no registry lookup)
cargo package -p gmcrypto-c    --list | sort
```

Expected:
- each packaging line names the crate at `v1.9.1`;
- **`LICENSE-APACHE` + `LICENSE-MIT` present in all three** (§3);
- packages contain `src/`, `Cargo.toml`, `Cargo.toml.orig`, `Cargo.lock`,
  `README.md`, `.cargo_vcs_info.json` (+ `include/`, `examples/` for `gmcrypto-c`;
  + `benches/`, `tests/` for `gmcrypto-core`);
- no `.git/`, `target/`, IDE folders, the `fuzz/` crate, or local secrets;
- `gmcrypto-c`'s package does **not** vendor `gmcrypto-core` source (the path dep
  is rewritten to the `=1.9.1` registry dep on publish).

**Only `gmcrypto-simd` can be dry-run before the release.** `--no-verify` is *not*
enough for `core`/`c`: their `=1.9.1` sibling is not on crates.io yet, and cargo
fails during dependency **resolution** ("failed to prepare local package for
uploading … failed to select a version for the requirement"), which happens
*before* the verification step `--no-verify` skips. This is the §3.D lockstep
contract behaving correctly, and it is exactly why the publish order is
`simd → core → c`.

So at review time, inspect `core`/`c` with `cargo package --list` (which does not
consult the registry) and treat a *resolution* failure on their dry-run as
expected. Anything else — a packaging error, a missing licence file, an
unexpected path — is a real finding. At **real** publish time each crate is
published in order and the next one's full verify resolves the now-live sibling.

Useful side effect: the failed dry-run enumerates the published candidates from
the crates.io index, which is an authoritative way to confirm the current max
published version (check 1.6 above) even when the crates.io HTTP API is
unreachable.

## 12. The publish sequence (only after GO)

```bash
cargo publish -p gmcrypto-simd
# wait for the index to update, then:
cargo publish -p gmcrypto-core
cargo publish -p gmcrypto-c
git rev-parse HEAD                                # MUST be the reviewed SHA
git tag -s v1.9.1 <reviewed-sha> -m "gm-crypto-rs v1.9.1"   # SSH-signed (gpg.format=ssh)
git push origin v1.9.1
gh release create v1.9.1 --title "v1.9.1" --notes-from-tag   # or curated notes
```

**Name the reviewed SHA on the tag.** A bare `git tag -s v1.9.1` tags whatever
`HEAD` happens to be. The reviewed commit is frozen (see the header) while `main`
moves on, so a maintainer finishing in an everyday checkout would tag a *later*
tree than the one crates.io received — a silent tag ⟷ registry mismatch that is
awkward to correct, since the published archive is immutable. Publish from a
checkout of the reviewed commit and pass that SHA explicitly.

**Post-publish verification** (once crates.io propagates):

```bash
for c in gmcrypto-simd gmcrypto-core gmcrypto-c; do
  curl -s "https://docs.rs/crate/$c/1.9.1/status.json"
done
```

Expect `{"doc_status":true,"version":"1.9.1"}` for each. A green `cargo doc` in CI
does **not** guarantee the docs.rs build; a failure is fixable without
republishing (trigger a rebuild from the crate's docs.rs page).

Then download one published archive and confirm the licence text really shipped —
the one check that closes this release's own defect:

```bash
curl -sL https://static.crates.io/crates/gmcrypto-core/gmcrypto-core-1.9.1.crate \
  | tar tzf - | grep -i license
```

Finally, confirm the tag really points at the reviewed commit:

```bash
git rev-list -1 v1.9.1     # must equal the reviewed SHA
```

## 13. Final go/no-go

Ship only when:
- §0 confirms the delta is behavior-free; §1–§7 and §9–§11 pass;
- **§3 shows licence text in all three archives** (the release's whole purpose);
- §8 shows no CT regression;
- `CHANGELOG.md` `[1.9.1]` has the final release date;
- the maintainer has the crates.io token + SSH tag-signing key ready.

[BLOCK / WARN / INFO] short title
