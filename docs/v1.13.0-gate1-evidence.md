The gate ran **once**, on 2026-09-04, against `b0b1be4`.

## Why this run is not content-free

The `crates/` + `Cargo.toml` delta from the published 1.12.0 (`b0c6679`) to
the candidate is ten files, +1 220 / −18:

| File | Nature of change |
|---|---|
| `Cargo.toml`, `crates/gmcrypto-core/Cargo.toml`, `crates/gmcrypto-c/Cargo.toml` | version `1.13.0`; sibling pins `=1.13.0` — one line each. The workspace `zeroize` dependency additionally gained its `alloc` feature (#193) |
| `crates/gmcrypto-core/src/sm4/{gcm,ctr,cbc,ccm}_streaming.rs` | `Zeroize` + `ZeroizeOnDrop` derives on every streaming type and the private `GhashAcc`; four consuming methods refactored to satisfy the generated `Drop` (E0509) with **public signatures, outputs and the `ct_eq` gate unchanged** |
| `crates/gmcrypto-c/src/lib.rs`, `include/gmcrypto.h`, `tests/c_smoke.rs`, `examples/sm4_ccm_streaming.c`, `README.md` | eight new `gmcrypto_sm4_ccm_{encryptor,decryptor}_*` symbols, header regenerated (pure addition), `c_smoke` 97 → 109, a tenth example |

What the gate exercises of that delta, and what it does not:

- **The `zeroize` feature flip and the sibling pins** are exactly what a
  downstream `[patch]` override tests: phase 2 resolves the envelope's graph
  against the candidate with `zeroize`'s `alloc` feature now enabled through
  `gmcrypto-core`, builds and lints it under both configurations, and the
  boundary scan proves no absolute path was written into the export (the
  v1.11.0 lesson, `docs/v1.11.0-gate1-evidence.md` §4).
- **The single-shot paths the envelope depends on are untouched by this
  cycle** (`sm4::mode_ccm`, `mode_gcm`, SM2, SM3, X.509): #193 changed only
  the streaming types, and #194 changed only `gmcrypto-c`, which the envelope
  does not consume. The gate confirms that by construction — its
  `standard_vectors` target drives the OpenSSL SM4-CCM baseline vector
  through `mode_ccm::decrypt` under `aead` (5 passed, phase 2) exactly as in
  the 1.12.0 run.

Every per-target count in both phases is identical to the 1.12.0 run
(`docs/v1.12.0-gate1-evidence.md`) — 147/13 and 189/15 in phase 1 and the
same per-target totals across phase 2. For a release whose Rust surface
change is additive impls, counts moving would have been the signal; they did
not move.

The Rust public-API change is additive (`Drop` + `Zeroize` impls for six
types; nothing removed). `cargo-semver-checks` against the crates.io 1.12.0
baseline was green on #193, and `docs/api-baseline/gmcrypto-core.txt` grew
by 48 additive lines. The C ABI is not covered by either instrument; the
committed header diff (+154, pure addition) on #194 is its record.

## What this gate does and does not establish

It establishes that `gmcrypto-envelope-lite` 0.4.0 at its current tip
(`e5162d8`) builds, lints, and passes its full suite against this candidate in
both configurations it ships (`default` and `--features aead`).

It does **not** exercise `sm4-bitsliced-simd` — no envelope configuration
enables it — and it does **not** reach any SM4 streaming type or any
`gmcrypto-c` symbol: the envelope's tip references none of
`Sm4GcmEncryptor`, `Sm4GcmDecryptor`, `Sm4CtrCipher`, `Sm4CbcEncryptor`,
`Sm4CbcDecryptor`, `Sm4CcmEncryptor`, `Sm4CcmDecryptor` or `Zeroize` in its
sources or tests (checked 2026-09-04). The zeroize behaviour rests on this
crate's in-module tests that call `zeroize()` and inspect the wiped fields,
the unchanged chunked-equals-single-shot matrices and KATs, and the three
differential streaming fuzz targets; the C ABI rests on `c_smoke` (109) and
the CI example compile. That is the intended coverage split for a release
whose new surface has no downstream consumer yet.

It says nothing about the docs.rs render or the crates.io pages, which are
observable only after publish (the §13-style post-publish checks in
`docs/v1.11.2-release-review.md` are the template).

## Declared downstream requirement

The envelope declares `gmcrypto-core = { version = "1.11", features =
["x509"] }`. A caret `1.11` requirement admits `1.13.0` as a SemVer-compatible
minor, so **no downstream bump is required** before this candidate ships. The
script's own line confirms it below: declared requirement `1.11`, candidate
version `1.13.0`. Per §8 the disposable gate copy is pinned to `=1.13.0` so
the override resolves regardless of the declared range — the real downstream
checkout is never modified.
